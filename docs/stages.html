Lunamux / Issue tracker

Build stages

Two stages, each one deployable and each one proving infrastructure rather than product. Revised from stages.txt.

What changed from stages.txt

  • Stages 2 and 3 merged. OAuth needs somewhere to put users; the database needs a reason to exist. Splitting them meant Stage 2 would have had to invent a throwaway session mechanism it then threw away in Stage 3.
  • The iframe embed moves into Stage 1. Framing is where the unpleasant surprises live, and it's the thing the whole design is premised on. Proving the deploy works standalone proves the wrong thing.
  • Multi-project support stays out entirely — your call, and I agree with the reasoning. Nobody is using this and won't for a long time. See Deliberately deferred at the bottom for the one place this leaves a mark.

Stage 1 Walking skeleton, embedded

A counter, in an iframe, on the real site, on the real domain, from a real container. No auth, no persistence.

Deliverables

  • Kotlin Multiplatform project: :clientServer (shared DTOs + HttpClient) → :client (backing view model) → :server (Ktor, JVM) / :web (Kotlin/JS IR). The server serves the JS bundle.
  • The web view is built with Kotlin DOM APIs — no Compose — styled to the Lunamux palette.
  • A CounterBackingViewModel holding the count in memory, exposing a single StateFlow<State> for the whole view, with an onIncrementTapped() intent. The view subscribes and re-renders the display.
  • Docker container, deployed to Railway.
  • Subdomain issues.lunamux.dev, Cloudflare DNS → Railway.
  • A secret Issues tab on lunamux-web that embeds it — details below.
  • An instructions HTML: domain config, Railway config, Docker deploy.

Do this before the first deploy, not after

Set the Railway hard usage limit (Workspace → Usage → Usage Limits). The soft limit only emails you; the hard limit is the one that actually takes workloads offline, which is the behaviour you asked for when you wrote "I need to ensure that I cannot get surprise bills due to unsurprising traffic." Minimum is $10, set per-workspace. It takes two minutes and it belongs in front of the first public URL, not behind it.

The secret Issues tab

Good news: lunamux-web already does exactly this for the Demo page, so this is a copy of a pattern that works rather than a new one. The demo iframe ships with a data-src and only gets a real src the first time its page is shown, so visitors who never open it never load the bundle. The Issues tab wants the same treatment.

Four small edits, gated on a query parameter:

// content.js — nav is data, so the gate goes here.
// Only push the tab when ?issues=1 is present.
nav: [
  { id: "about",    label: "About",    href: "#/" },
  /* … */
  // appended at runtime by render.js when the param is set
]

// render.js — mirror the demo page exactly
document.getElementById("page-issues").innerHTML =
  '<section class="issues">' +
    '<iframe id="issues-iframe" title="Lunamux issues" ' +
      'data-src="https://issues.lunamux.dev/"></iframe>' +
  '</section>';

// script.js — register the page + lazy-load, like ensureDemoLoaded()
var pages = { /* … */ issues: document.getElementById("page-issues") };

The gate itself is just new URLSearchParams(location.search).has("issues"), checked before the nav is rendered. The URL you'd use is https://lunamux.dev/?issues=1#/issues — note the param lives in the query string, before the hash, so it survives the hash router untouched.

"Secret" here means undiscoverable, not protected

lunamux-web is a static site. The tab, the parameter name and the issues.lunamux.dev URL are all sitting in content.js for anyone who opens view-source, and the server itself is publicly reachable regardless of what the marketing site does or doesn't link to. That is completely fine for what you actually want here — no links, nobody stumbles in — as long as you don't later mistake it for an access control. When Stage 2 adds real users, the server enforces that itself. The query param never guards anything but the tab's visibility.

What Stage 1 is really testing

The counter is set dressing. The questions being answered are: does Kotlin/JS produce a bundle that actually runs when served from the JVM server; does the container build and boot on Railway; does Cloudflare → Railway resolve with a working certificate; and does the whole thing survive being put in an iframe on another origin. That last one is why the embed can't wait.

Concretely, framing means the server must send Content-Security-Policy: frame-ancestors https://lunamux.dev. That is the only mechanism that works — X-Frame-Options: ALLOW-FROM is dead and no browser honours it. Get it wrong and you get a blank rectangle with a console error, which is a five-minute fix in Stage 1 and a confusing detour later.

One quiet piece of luck

issues.lunamux.dev and lunamux.dev share a registrable domain, so the embed is same-site. Browsers key their third-party restrictions on site, not origin, which means cookies just work in the iframe and you need none of the misery — CHIPS, Storage Access API, partitioning — that a genuinely cross-site embed would force on you in Stage 2. This is worth protecting: if the tracker ever moves to a different apex domain, that decision quietly costs you the auth model.

Exit criteria

Load https://lunamux.dev/?issues=1#/issues in Chrome and Safari. The counter increments inside the iframe. Redeploy the container; the count resets to zero and that's correct. The Railway hard limit is set. No console errors.

Stage 2 Identity and persistence

Sign in with Google and GitHub. Real users in a real database. Still no email, still no issues.

Deliverables

  • OAuth sign-in with Google and GitHub. No custom email accounts, no mail transmission.
  • An embedded SQLite database on a Railway volume.
  • A users table (provider, provider id, display name) and a per-user persisted counter — the counter is still the POC payload, it just belongs to someone now and survives redeploys.
  • An instructions HTML: Google Cloud console and GitHub OAuth app configuration.
  • Instructions and/or scripts for creating the Railway volume.

The one that will bite: OAuth cannot be framed

Google's consent endpoint responds with X-Frame-Options: DENY. I verified this directly:

$ curl -I "https://accounts.google.com/o/oauth2/v2/auth?client_id=…"
HTTP/2 302
x-frame-options: DENY          ← the entire answer

It is unframeable, permanently, by design, and there is no header you can set on your side to change that. A full-page redirect flow inside the iframe is equally dead — it would try to navigate the frame to Google, and Google refuses to be the thing in the frame.

The supported path is a popup: Google Identity Services' initCodeClient with ux_mode:'popup'. Which in turn needs allow="identity-credentials-get" on the iframe element in lunamux-web, and Cross-Origin-Opener-Policy: same-origin-allow-popups on your server — without the latter the popup opens and then can't talk back to the opener, which presents as a login that silently does nothing.

Test the sign-in through the iframe from the first commit of this stage. Tested at issues.lunamux.dev directly it will pass, and that pass tells you nothing about the configuration you're actually shipping.

Database: SQLite on a volume

Attach a Railway volume and put the database file on it. The container's own filesystem is a writable layer that is discarded on every redeploy — this is precisely the concern you raised in the plan, and the volume is the answer to it. The file lives at the mount path; the deploy replaces everything around it and leaves it alone.

Open it with these pragmas and you can stop thinking about it:

journal_mode = WAL      -- concurrent readers alongside the writer
busy_timeout = 5000     -- wait rather than throw SQLITE_BUSY
synchronous  = NORMAL   -- correct and fast under WAL
foreign_keys = ON       -- off by default, which surprises everyone

The implication worth naming out loud

A volume binds you to exactly one instance. Railway volumes attach to a single service, and SQLite's locking is filesystem locks — which coordinate correctly between threads on one machine and not at all between two. Two instances on one SQLite file over a network filesystem is the classic silent-corruption recipe, not a "runs a bit slow" problem.

This is the right trade for now and for a long while — one container will serve your traffic without noticing it — but it means horizontal scaling is the thing you gave up, and the day you need it, the move is to Postgres rather than to more containers. §7 of the analysis covers what that migration looks like. Knowing you chose this beats discovering it.

Backups are deliberately not in this stage. A VACUUM INTO on a schedule is the cheap version when you want one; Litestream is the real answer and belongs with real data.

Exit criteria

Sign in with Google inside the iframe, in Chrome and Safari. Sign in with GitHub the same way. Increment the counter, redeploy the container, sign back in — the count is still there. That last step is the whole stage in one action: it proves identity and persistence together, which is exactly why they merged.

Later Deliberately deferred

Named here so they're choices, not oversights.

DeferredWhy it's safe to wait
Multi-project support Nobody's using it and won't for a long time; the shape will have stabilised by then. The only cost is that URLs minted now are single-project ones, so adding /p/{slug}/ later means either a redirect or accepting that Lunamux is the unprefixed default. Both are fine. It's a real cost, just a small and well-understood one.
Email — sending and receiving Entirely dependent on self-service accounts, which OAuth removes the need for. Resend + Cloudflare Email Routing whenever it's wanted; §8 of the analysis has it costed and configured.
Issues themselves Correct to be last. Once identity, persistence, framing and deploys are proven, issues are just a schema and some views — the ordinary part of the work, and the part with no infrastructure risk in it.
Litestream / real backups There is no data worth protecting until there is. Worth wiring up before the first issue you'd be upset to lose, and not before.
Docker config surface, open-sourcing Configurability is shaped by what turns out to vary, which you'll know after running it yourself for a while. Guessing now means guessing wrong.
