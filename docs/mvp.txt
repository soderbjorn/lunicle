CLARIFICATIONS #1

* It's important to clarify we are still iterating. As such we don't yet have to care about migrations. In fact you can wipe the database table for this rework. Maybe after this version we might need migrations after I decide things have settled a bit.
* I decided to skip JSON blobs for now. Let's go with regular columns. Hence skip settings blob.
We add roles table, which contains hardcoded list which the user cannot edit like "create_issue", "comment_on_issue", "change_unowned_issues" (change anything on issues they did not create).
We have project_roles table which associates users with a role in a specific project, they can have many roles. 
* In users table, display_name should be a nullable text that the user can optionally set to override their display name. It should not carry anything from the account.
* We add provider_name instead for the name retrieved from Github/Google.
* In projects table, skip name_folded. The user should not be able to create two projects with same name that differ only be casing. Skip settings blob too. Add a column "name_prefix", this is what gets appended before issue names in an issue name like FOO-123.
* Defaults in tables get added on first creation of database.
* We add a table "labels". It holds a list of labels, with one column the ID of the project for which it applies. It can have duplicates (for different projects). By default we add "Bug", "Feature", "Improvement", "Codebase". 
* We add a table "components". It holds a list of components, with one column the ID of the project for which it applies. It can have duplicates (for different projects). By default we add "Desktop", "Server", "Android and "iOS".
 * We add a table "status". It holds a list of statuses, with one column the ID of the project for which it applies. It can have duplicates (for different projects). By default we add "New", "Backlog", "Ready for development", "In progress", "Ready for test", "Testing", "Completed", "Closed".
 * We add a table "issues". Each issue has reference to its project, one or more labels, one or more components, and a status. Default status is "New". It also has a number (in addition to the ID). The project's prefix combines with "-" to produce the displayed ticket number like FOO-123. It also has a label, which is the short description. It also has a description, which is the long description in markup format. It also may have multiple comments inside of it. It also has a date timestamp and the id of the user who made it. can have multiple binary/image attachments associated with it also, you propose how to store those.
* We have comment table, which has datetimestamp, user id, markdown, and can have multiple binary/image attachments associated with it.

 To make these relationships like "one issue can have many labels assigned, out of the labels available to the project" perhaps you need trickery like additional decided. Up to you to decide.

The admin role can do everything. That's all we need to know for now. We don't have to care so much about roles yet.
* in the main content area, if a project is selected, we see a Issues list arranged by Status (each column represents a status). Each issue is listed with its prefix and number like "LMX-123: Unable to remove user". We can click an issue to open it in a modal dialog where the user can either read it, or if they have permission change it also. There is a button to add a new issue. Inside the issue modal dialog user can delete it also.
