01Verdict & recommended stack

The short version, before the reasoning.

Feasible

Every part of this plan works. Nothing here requires a compromise you'd regret. Two things are harder than they look — OAuth inside an iframe, and cookies once you embed on domains you don't own — and one thing is easier than you fear: surprise bills are genuinely preventable on Railway, unlike on most clouds.

The three things worth changing your mind about

  1. Railway's hard limit is a kill switch, not a throttle. It answers your "no surprise bills" requirement exactly — but the way it protects you is by taking your site offline. That is the correct trade for a hobby project; just know that's what you bought.
  2. Multi-project embedding breaks the cookie story. Embedding on lunamux.dev is same-site and trivially fine. Embedding on someone else's domain is cross-site, and Safari and Firefox block that by default today. The fix is per-project custom domains, and it's much easier to design in now than to retrofit. This is the single most consequential finding in this document — §3.
  3. SQLite is the right call, and Postgres-as-an-option is a trap. Not for performance reasons — for maintenance ones. Supporting both means running your whole test suite against both, forever. §6.

02Multi-project support

Your late addition, and it's load-bearing — it changes the answers in §3, §8 and §10.

The model

Multi-project, single-operator. Each deployment has exactly one operator who owns every project on it — yours has your projects; anyone else deploys their own container for theirs. This is software you ship, not a platform you run, and that distinction removes a category of work.

Wanting one server to host issue tracking for several projects, each embeddable in that project's own website, is a reasonable and common shape. It's also the requirement that turns three "trivial" decisions into real ones. Worth designing for now even if Lunamux is the only project for a year, because two of the three are painful to retrofit.

Multi-project earns its keep immediately. Without it, every project you start needs its own container, volume, domain and Railway service — and Railway's $5 floor applies per service. With it, a new project is a five-line entry in a config file on infrastructure you already pay for. That's the feature paying for itself at project number two.

The data model is the easy part

A project table with a slug, and a membership table joining accounts to projects with a role. Issues belong to a project. Accounts are global — one account, one verified email, membership in many projects. Don't scope accounts per project; you'd be re-verifying the same human's email once per project, and email verification is your most abuse-prone endpoint (§8).

-- the shape, roughly
account(id, email UNIQUE, email_verified_at, google_sub UNIQUE NULL, display_name)
project(id, slug UNIQUE, name, theme_json, allowed_origins, created_by)
membership(account_id, project_id, role)  -- owner | maintainer | reporter
issue(id, project_id, number, title, body, state, author_id, ...)

Give issues a per-project sequential number alongside the global id — people expect #42 to mean the 42nd issue in their project, not the 42nd row in your table. This is a small thing that is deeply annoying to add later, once URLs are public and bookmarked.

The three decisions it forces

DecisionSingle-tenant answerMulti-tenant answer
Embedding origin One iframe on lunamux.dev. Same-site, cookies just work. Each project's site is a different registrable domain → cross-site → cookies blocked by default in Safari and Firefox. See §3.
Sending domain All mail from send.lunamux.dev. Settled by the single-operator model: one sending identity per deployment, set by env var. Never per-project DKIM, per-project reputation, or per-project deliverability tickets. See §8.
Theming Hardcode the Lunamux palette. Theme becomes per-project data. Cheap if it's CSS custom properties from day one, expensive if you hardcode colours first. See §10.

Accounts are public. Projects are not.

Easy to conflate, and the distinction is where your abuse surface lives. Project creation is operator-only — a config file, not a signup form. But account creation is public: anyone on the internet can register to file an issue against Lunamux, which is the entire point. So §8's abuse section applies at full strength — rate limit per target email address, Turnstile on the form, a hard daily send cap in code. "Only my projects" sounds like a private tool; it's really a public signup form attached to a private project list.

What the single-operator model does remove: cross-tenant abuse liability, content moderation for strangers' projects, per-tenant support, and project scoping as a security boundary between mutually distrusting parties. Scoping is still a correctness concern — don't leak project A's issues into project B's view — but getting it wrong is a bug, not a breach.

How projects get created: a config file, not an admin UI

Because projects are operator-controlled configuration rather than user data, you don't need an admin UI for v1 — which deletes the single largest chunk of pre-launch work. Declare them in a file, mount it, upsert into the DB by slug at startup:

# /config/projects.yaml — mounted, version-controlled, no UI needed
projects:
  - slug: lunamux
    name: Lunamux
    allowed_origins:
      - https://lunamux.dev
    theme:
      bg:        "#04090f"
      panel:     "#070f1a"
      accent:    "#4dc8f5"
      accent_hi: "#66d9ff"
      head:      "#eaf3fb"

Version-controlled, reviewable, revertible. Self-hosters get a file they can read rather than six screens to click through, which is what keeps your README short. Theme and origin allowlist live together, which is exactly where §3 and §10 want them. And upsert-by-slug is idempotent, so restarts are free.

This is a deliberate exception to the "env vars, not config files" rule in §11 — env vars are right for scalars like a database path or an API key, but a nested list of projects with themes and origin lists is not a scalar, and PROJECTS=lunamux:Lunamux:#04090f,… is clever for a week and miserable forever.

Embed URL shape

Put the project in the path, not a query parameter — it's cleaner to route, cache and reason about, and it makes the origin allowlist check a natural part of routing:

https://issues.lunamux.dev/embed/lunamux         ← project slug in path
https://issues.lunamux.dev/embed/lunamux/42      ← deep link to issue #42

Store an allowed_origins list per project and use it to generate the frame-ancestors CSP header per request. That way project A's tracker can't be framed by project B's site, and you get a real answer to "who is allowed to embed this" instead of a wildcard.

03Embedding & the auth problem

The hardest section, and the one where the multi-project requirement bites. Read this one properly.

Crux

Embedding an authenticated app in an iframe is fine when the embedding site and the app share a registrable domain, and genuinely difficult when they don't. Your plan does both.

Same-site vs same-origin — the distinction everything hinges on

Browsers apply third-party restrictions based on the site (the registrable domain, eTLD+1), not the origin (scheme + host + port). So:

Parent pageFramed appSame-origin?Same-site?Do cookies work?
lunamux.devissues.lunamux.devNoYesYes — everywhere, by default
someproject.comissues.lunamux.devNoNoNo — blocked in Safari & Firefox
someproject.comissues.someproject.comNoYesYes — everywhere

Row one is your Lunamux tab, and it's the happy path: WebKit's own tracking-prevention policy states that site.example, www.site.example and s.u.b.site.example are all the same party, so ITP doesn't engage. Firefox's Total Cookie Protection partitions by top-level site, which here is lunamux.dev either way. A plain SameSite=Lax; Secure; HttpOnly cookie works in every browser, including Safari, with no special handling.

Row two is what multi-project gives you by default, and it's the bad one. Safari has blocked third-party cookies outright since 2020. Firefox partitions them, so a session set in one context isn't visible in another. Chrome still permits them (see below) but blocks them in Incognito.

Row three is the fix, and it's cheap: each project points a CNAME at your server. issues.someproject.com → your Railway app. Now the frame is same-site with its parent, and the whole problem evaporates — no CHIPS, no Storage Access API, no partitioned-cookie edge cases, no per-browser testing matrix. It costs one DNS record per project, plus TLS provisioning that Railway does for free.

And per the single-operator model in §2, you own every domain involved — so this is a record in a zone you already administer, not a coordination problem with a third party. The same holds for self-hosters, who own their own projects' domains. What looked like a defensive design is really just the obvious one.

For reference, only two of your projects have sites deployed today: lunamux-web → lunamux.dev and termtastic-web → termtastic.soderbjorn.se. So future projects will land either on their own domain or on a soderbjorn.se subdomain. If most end up as soderbjorn.se subdomains, hosting the tracker at issues.soderbjorn.se would make those same-site for free, with only lunamux.dev needing its own CNAME — but the uniform per-project CNAME works everywhere for one record either way, so I wouldn't optimise for it.

Recommendation

Make a per-project custom domain the supported way to embed. Iframe issues.lunamux.dev on lunamux.dev today because it's free and it works; but design the server so a project's embed host is a per-project setting from the start — it's already in projects.yaml next to allowed_origins (§2). Retrofitting this after you've shipped cross-site cookie workarounds means throwing the workarounds away — and the workarounds are the expensive part.

If you must support cross-site embedding anyway

The escape hatch is CHIPS — Set-Cookie: session=…; SameSite=None; Secure; Partitioned. The cookie is then scoped to the (top-level site, your site) pair: the user is separately logged in on each embedding site, which for an issue tracker is arguably correct anyway. Combine with the Storage Access API for browsers that need an explicit grant. It works, but you're now testing three browsers' partitioning behaviour and accepting SameSite=None, which weakens your CSRF posture. Do it only if a project genuinely can't add a DNS record.

Google OAuth cannot be framed. Ever.

I checked this directly rather than trusting the documentation:

$ curl -I "https://accounts.google.com/o/oauth2/v2/auth?client_id=..."
HTTP/2 302
x-frame-options: DENY          ← the entire answer

DENY, not SAMEORIGIN. There is no allowlist, no client-ID setting, no frame-ancestors negotiation. Framed, you get "accounts.google.com refused to connect". This is deliberate: a framed consent screen hides the real URL bar, which is the entire security model of OAuth consent. It will not change.

But you don't need it to. Google Identity Services explicitly supports your exact topology. From their FedCM migration guide, verbatim: "Only using One Tap in cross-origin but same-site iframes is a supported method" — with https://login.example.com embedded in https://www.example.com as the worked example. That is row one of the table above, one-for-one.

What this means concretely:

  • Use google.accounts.oauth2.initCodeClient with ux_mode:'popup', triggered by a real user click. window.open creates a top-level window, which is not framed, so X-Frame-Options never applies. This is the standard, compliant path.
  • Add allow="identity-credentials-get" to the iframe tag. FedCM is permission-policy gated and cross-origin frames are opted out by default — and Google counts a subdomain as cross-origin. Miss this and it fails quietly.
  • Set Cross-Origin-Opener-Policy: same-origin-allow-popups. Plain same-origin severs window.opener, so the popup can't post the auth code back and you'll debug it for an hour.
  • Never use ux_mode:'redirect' inside the frame. It redirects the iframe, Google refuses to render framed, and your app disappears. If you need redirect mode — Google's docs say ITP forces it on iOS — it must target the top-level window.

Don't confuse two Google policies

The disallowed_useragent / "embedded webview" policy you may have read about targets native webviews (WKWebView, Android WebView). It does not apply to browser iframes, and a window.open popup is a compliant system browser. Your blocker is X-Frame-Options, not the user-agent policy. Useful to know when you get to the mobile apps.

Third-party cookies: what actually happened

This changed direction publicly several times and most writing about it is stale, so briefly, for the record:

  • Chrome never deprecated them. In April 2025 Google confirmed it would keep third-party cookies and abandon the standalone choice prompt. In October 2025 it retired around ten Privacy Sandbox APIs (Topics, Protected Audience, Attribution Reporting, Related Website Sets). CHIPS and FedCM survived — the two you'd actually use.
  • Safari has blocked them by default since 13.1 (2020), keyed on registrable domain.
  • Firefox partitions rather than blocks, default for everyone since 103 (2022).

If you see an article promising a Chrome "Privacy Choice" prompt in 2026, it's not supported by any official source. And note that requestStorageAccessFor() was retired with Related Website Sets in October 2025 — MDN still lists it as supported in Chrome, which is a live documentation error. Don't build on it.

The sharpest edge in the whole design

github.io is itself a public suffix. The entire same-site analysis above depends on lunamux.dev being the registrable domain. If the site is ever reached via soderbjorn.github.io, the eTLD+1 becomes soderbjorn.github.io, which is genuinely cross-site from issues.lunamux.dev — Safari and Firefox break instantly, Chrome breaks in Incognito. Your CNAME file already pins lunamux.dev; keep "Enforce HTTPS" on and make sure the .github.io URL redirects rather than serves. This is invisible until it isn't.

Headers the tracker must send

# per-request, generated from the project's allowed_origins
Content-Security-Policy: frame-ancestors 'self' https://lunamux.dev
Cross-Origin-Opener-Policy: same-origin-allow-popups
# and critically — do NOT send X-Frame-Options at all
  • X-Frame-Options: ALLOW-FROM is dead — modern browsers ignore the header entirely when they see it. Only DENY and SAMEORIGIN function, and there is no XFO way to allow a specific cross-origin parent. frame-ancestors is the only mechanism.
  • CSP3 says frame-ancestors overrides XFO, and browsers implement that — but ship without XFO anyway rather than betting on override precedence against corporate proxies and scanners.
  • Audit Ktor's default headers. Most server stacks inject X-Frame-Options: SAMEORIGIN by default, and since issues.lunamux.dev is a different origin from lunamux.dev, SAMEORIGIN blocks you. This is the most likely cause of a mysterious "it just won't frame" afternoon.
  • frame-ancestors cannot be set via <meta> — HTTP header only — and it does not fall back to default-src.
  • Don't use sandbox on the iframe. It's your own app. Without allow-same-origin the frame gets an opaque origin: no cookies, no storage, no session. And allow-scripts allow-same-origin together let the frame remove its own sandbox anyway. The only config where your app works is the one that provides no protection.

GitHub Pages as the parent is a non-issue — a parent needs no headers to frame someone; permission is entirely the child's decision. Pages currently sends no XFO, no CSP, and can't set custom headers at all, which doesn't matter here. One real trap: if lunamux.dev ever adds a <meta http-equiv="Content-Security-Policy"> with default-src, then frame-src inherits from it and silently blocks your iframe. Add frame-src https://issues.lunamux.dev explicitly if so.

Session storage: use a cookie, not localStorage

It's tempting to dodge cookies entirely by keeping the session token in the iframe's localStorage — and in the same-site case it isn't even partitioned, so it would work. Don't:

  • You lose HttpOnly. With an HttpOnly cookie, an XSS in your Kotlin/JS bundle can act as the user but can't steal the credential. With localStorage it walks off with a portable token that works from anywhere.
  • Safari caps script-writable storage at seven days → silent logouts.

Note this differs from FramnaFolk, which stores its session token in localStorage. That's defensible there — it's an internal tool behind Google sign-in — but this app takes public signups on a domain you're staking a product name on. Use Set-Cookie: session=…; Secure; HttpOnly; SameSite=Lax; Path=/ with no Domain attribute, so it stays host-only and isn't exposed to lunamux.dev or sibling subdomains.

The stateless AES-GCM session token pattern from FramnaFolk (auth/TokenEncryption.kt) is worth reusing wholesale — it gives you no session table, encrypted refresh tokens riding inside the token, and transparent rotation via a response header. Just deliver it in an HttpOnly cookie rather than to JavaScript.

UX realities of iframing

  • Height: no CSS-only cross-origin solution exists. ResizeObserver in the child → postMessage → parent sets height. Always pass an explicit targetOrigin, never *, and always verify event.origin on receipt. Note iframe-resizer relicensed to GPL-3.0 at v5 — hand-roll the ~30 lines instead.
  • URL sync: the parent cannot read the frame's URL (contentWindow.location.href throws SecurityError), so child→parent routing must go via postMessage. Your site's hash router is fine here, but don't re-assign iframe.src on hash changes — that hard-reloads the app and destroys its state.
  • Back button: no clean fix. iframe navigations push onto the joint session history, so a user who clicks through eight issues and hits Back walks back through eight in-app states instead of returning to your marketing site. The WHATWG issue for an opt-out is still open. Mitigate with history.replaceState internally. This is the strongest argument against the iframe, and worth weighing against just linking out to issues.lunamux.dev with shared styling.
  • Modals are clipped to the iframe box and can't overlay parent chrome. For an issue tracker with dialogs, this is often what actually kills the embedded feel.
  • iOS Safari sizes iframes to content and ignores your height — needs an overflow:auto wrapper.

The alternative worth keeping in your pocket

If the back button or modals become annoying, the clean escape is to reverse-proxy a path so the app is genuinely same-origin: lunamux.dev/issues → your Railway app. Every problem in this section evaporates at once — same origin, so no cookie question, no framing headers, no postMessage, no back-button weirdness.

GitHub Pages cannot proxy, at all. But a Cloudflare Worker can (free tier: 100k req/day; a proxy burns essentially no CPU since fetch wait doesn't count), and if you moved the site to Netlify, Vercel or Cloudflare Pages Functions it's a one-line rewrite rule. Note Cloudflare's Rules-based origin override is Enterprise-only, and Pages' _redirects won't proxy to external hosts — it's Workers or Functions specifically.

Worth noting this only helps your own site. Other projects embedding you still need the per-project CNAME. So the CNAME design isn't wasted either way — which is another reason to build it first.

04Kotlin Multiplatform architecture

You've built this exact shape twice. Copy it.

Your instinct here is well-founded and you have a proven template: FramnaFolk's module structure is precisely what you're describing, and Lunamux already ships a Kotlin/JS DOM client. There's no research question to answer — just a recommendation to follow your own precedent rather than reinventing.

ModuleTargetsContents
:clientServerjvm, js, android, iosArm64, iosSimulatorArm64@Serializable DTOs, the shared HttpClient and Json config. Depends on nothing internal.
:clientsame setBacking view models, repository, API service. Depends on :clientServer.
:serverJVM only (not KMP)Ktor + Netty, SQLDelight, routes. Depends on :clientServer.
:webjs(IR) browserDOM rendering via kotlinx-html. Depends on :client + :clientServer.

Add :androidApp (Compose) and an Xcode project consuming the KMP framework (SwiftUI) later — declaring the targets now in :client and :clientServer costs nothing and means the mobile apps are additive rather than a refactor.

The backing view model pattern

In FramnaFolk there's no base class — it's a convention, and it holds up well: each backing VM is a plain class owning a CoroutineScope(SupervisorJob() + Dispatchers.Main), with a private MutableStateFlow(State()) exposed as val stateFlow = _stateFlow.asStateFlow(), a nested data class State, and onXxxTapped() intent methods. Platforms wrap it:

  • Web: collect stateFlow in a coroutine, call your render function. FramnaFolk skips per-screen wrappers on web entirely and uses the backing VMs directly from render code — fine, and less ceremony.
  • iOS: an ObservableObject with @Published private(set) var state, bridged via the 20-line FlowObserver helper (Swift can't consume Kotlin Flow directly). This is the single most reusable piece of FramnaFolk.
  • Android: an AndroidX ViewModel forwarding intents through viewModelScope.launch.

I'd consider formalising it this time — a small abstract class BackingViewModel<S> owning the scope and the state flow. FramnaFolk's eight independent classes work, but they repeat the same six lines eight times, and a base class makes the contract discoverable for anyone else reading an open-source repo.

Kotlin/JS, not Wasm — and one warning from your own codebase

Kotlin/JS (IR) with kotlinx-html is the right call: it's what both existing projects use, the tooling is mature, and :clientServer in Lunamux already declares a wasmJs target if you want to experiment later.

Read this before you configure the JS build

Lunamux's server module deliberately embeds the development JS bundle rather than the production one, with a comment explaining that Kotlin/JS production DCE and name mangling miscompile that codebase — <mangled> is not a function at runtime. It costs ~25 MB versus ~4.5 MB, which is free over loopback but is not free over the public internet for an embedded iframe.

So: test jsBrowserProductionWebpack output early, not the week before launch. If you hit the same mangling bug, you need to know while the codebase is small enough to bisect. This is a known, real hazard in your own stack rather than a hypothetical.

Also worth stealing from FramnaFolk's server: the pipelineRoute + Handler<S, T> + HandlerResult.Continue/Stop DSL gives you composable per-route middleware with structured logging built in. If you reuse it, consider fixing the unchecked casts — the current version type-checks each handler but casts through Handler<Any?, Any?> when chaining, so a mis-ordered handler list fails at runtime rather than compile time.

05Hosting & surprise bills

Your "no surprise bills" requirement has a clear winner, and it's the one you already picked.

Railway

Of the five platforms I checked, Railway is the only one with a self-serve spend cap that actually stops workloads. Everyone else offers alerts, which are not a cap. Your instinct was right.

The feature, precisely

Railway's Usage Limits come in two flavours, and the difference is the whole ballgame:

  • Soft limit: "we will email you that this threshold has been met. Your resources will remain unaffected." A notification.
  • Hard limit: "all your workloads will be taken offline to prevent them from incurring further resource usage." Real enforcement.

Railway itself calls the hard limit "a possibly destructive action" — which is the tell that it's genuine. Details that matter:

  • Minimum hard limit is $10. You can't cap lower.
  • Scope is per-workspace, not per-project. Everything goes down together.
  • Warnings escalate at 75%, 90%, 100%.
  • Data and configuration survive — only deployments are removed. Raise the limit and Railway automatically redeploys.

So your worst case is $15 and an outage, not a $2 000 shock. Set a soft alert at $8 and a hard limit at $10, and the requirement in your plan is met.

Railway is a substantially better developer experience for a solo project. Take Railway. Revisit if you ever find the $10 ceiling binding, which at your scale you won't.

Railway gotchas specific to your stack

  1. Volumes and replicas are mutually exclusive, and volume-backed services have downtime on every redeploy — Railway prevents two deployments mounting one volume, so healthchecks can't give you a zero-downtime handover. For an issue tracker, a few seconds of downtime per deploy is fine. Just know it's structural, not a config mistake.
  2. Serverless / app sleeping will never trigger for you. Inactivity is judged on outbound packets, and Railway's docs explicitly name an open database connection pool as something that keeps a service awake. A JVM app with Hikari never sleeps. Also, the first request to a slept service "may return a 502" — rough for a JVM cold start. Don't plan around this feature.
  3. Healthchecks run at deploy time only. There's no ongoing liveness probe restarting a wedged process. If the JVM deadlocks at 3am it stays deadlocked.
  4. Non-root images may need RAILWAY_RUN_UID=0 for volume permissions — relevant since hardened JVM images commonly run non-root.
  5. Use Dockerfile, not Railpack. Nixpacks is deprecated; Railpack's Kotlin/Gradle support is unconfirmed. A Dockerfile sidesteps the question and gives reproducible builds. Wire up BuildKit cache mounts for the Gradle cache — it's the difference between a 1-minute and a 5-minute build.
  6. Custom domains and TLS are free and automatic, which is what makes the per-project CNAME plan from §3 practical. Verify the domains-per-service limit before onboarding many projects — Railway's limits reference page currently 404s.

On moving the marketing site to Railway — settled: don't

You asked whether it would help. It doesn't, and it costs you something real. The marketing site stays on GitHub Pages.

Why it's a non-issue. An iframe boundary is resolved by the browser, not by a server. Pages answers for lunamux.dev, Railway answers for issues.lunamux.dev, and neither host needs to know the other exists. A parent needs no headers to frame someone — permission is entirely the child's decision, so frame-ancestors and the Stage 2 Cross-Origin-Opener-Policy are both sent by Railway. Pages' inability to set custom headers is famous and irrelevant, because nothing is asked of it. Even allow="identity-credentials-get" is an attribute on the iframe element, so it's just markup in render.js.

The same-site property survives too — the part people expect to break. Same-site is computed from the registrable domain (lunamux.dev) and has nothing to do with hosting providers. Two subdomains of one apex are the same site whether they're served from one rack or two continents. Cookies in the iframe work regardless of who hosts what.

The argument against moving is your own constraint. Pages is free with no meter running. Railway bills by usage against a hard limit that takes workloads offline when tripped. Co-hosting merges the failure domains: marketing traffic would burn tracker budget, and hitting the cap would take the marketing site down alongside the tracker. Today those are cleanly separated — the tracker can go dark while lunamux.dev serves normally. That's the blast radius you want. 06Database: SQLite vs Postgres

Your SQLite instinct is right, your worry about persistence is right, and the fix is routine.

Why the file disappears — and the fix

Your concern is well-founded and the mechanism is worth stating exactly, because it's why this bites people. A container image is read-only layers; a running container adds one thin writable layer bound to that container instance. Anything not on a volume — including app.db — lives only there. docker restart keeps it (same container), so it looks like it works. A redeploy, a new image tag, or --force-recreate destroys the container and the layer, and the app comes back "clean". That's the trap: it works right up until you deploy.

The fix is a mounted volume, which Railway supports and which survives redeploys and new image versions:

DATABASE_PATH=/data/app.db          # env var, 12-factor
volume mounted at /data             # Railway: 5 GB on Hobby, $0.15/GB/mo

Mount the directory, never bind-mount the DB file itself — WAL mode creates app.db-wal and app.db-shm siblings, and Litestream wants a temp dir alongside. A single-file bind mount also pins an inode on Linux, so after a restore the container silently writes to a ghost file.

Pragmas that are not optional

PRAGMA journal_mode=WAL;      -- persistent in the file; required by Litestream
PRAGMA busy_timeout=5000;     -- without this, concurrent writes 500 immediately
PRAGMA synchronous=NORMAL;    -- safe AND recommended in WAL mode
PRAGMA foreign_keys=ON;       -- SQLite defaults this OFF, per connection

Set these via a connection-init SQL so they apply to every pooled connection, not just the first.

WAL on a network filesystem — the one way to lose everything

SQLite's docs are blunt: "All processes using a database must be on the same host computer; WAL does not work over a network filesystem." The WAL index is mmap'd shared memory, and NFS/EFS/SMB emulate mmap coherency and advisory locking at best. Two processes can each believe they hold the write lock. You don't get an error — you get silent corruption. On a local block volume (Railway volumes, Docker named volumes, EBS, Hetzner volumes) this is a non-issue. Document "do not put the data directory on a NAS/NFS mount" prominently — it's the most likely way a self-hoster destroys their data with your software.

Is SQLite actually adequate?

Not close to marginal. SQLite's own guidance puts the threshold around 100k hits/day and notes sqlite.org itself serves 400–500k requests/day on it. Expensify runs SQLite for millions of users. Their "use client/server instead" checklist has three triggers — data separated from the app by a network, high write concurrency, terabyte scale — and you hit none of them. Tens of users and megabytes of read-heavy data is two to three orders of magnitude inside the envelope.

The honest counterargument isn't performance, it's that Postgres has a boring, universally-understood backup story and SQLite makes you think about it. So:

Backups

Never cp or snapshot a live SQLite file — you'll copy a torn page set and find out at restore time. Two mechanisms, and I'd run both:

Litestream is healthy again, which is worth knowing if you last looked a year ago. v0.5 shipped October 2025 after the long v0.3.13 plateau, and releases are steady (v0.5.14 on 6 July 2026). Ben Johnson works on it at Fly.io. v0.5 is a real upgrade: a new LTX format, generations replaced by monotonic transaction IDs giving genuine point-in-time recovery, hierarchical compaction, CGO-free builds.

Two Litestream caveats

v0.5 cannot restore v0.3.x WAL files, and enforces one replica destination per database. Any pre-2026 Litestream tutorial you find will be wrong — use the official migration guide.

Run it as a sidecar container, not in the same container. The same-container pattern makes Litestream your process supervisor, and the naive version (litestream replicate & java -jar app.jar) gives you a shell as PID 1 that doesn't forward SIGTERM and exits 0 when the JVM dies while Litestream keeps the container alive — a "healthy" container serving nothing. Even done right, if Litestream crashes you get a healthy app that is silently no longer backed up. Sidecar, or -exec, or s6-overlay. Railway note: sidecars sharing one volume are awkward there, since volumes are per-service. On Railway specifically, litestream replicate -exec in one container is the pragmatic answer — it handles the single-process case properly. The nightly dump is your safety net against Litestream failing silently.

Add a startup assertion that the DB is on a different device than /. It catches the number-one self-hoster mistake — forgot the volume — before it costs anyone data rather than after.

The alternatives, briefly

  • Turso/libSQL — the Rust rewrite is real and the free tier is generous, but there is no official JVM SDK. The only option is a community JDBC driver speaking the remote HTTP protocol, which means embedded replicas — the entire reason to choose Turso — aren't available to you. You'd get a network round-trip per query: all of Postgres's downsides, none of its maturity. Skip.
  • Cloudflare D1 — HTTP-only, and Cloudflare says the REST API is for administrative use and you should build a proxy Worker. Your architecture becomes Ktor → HTTPS → Worker → D1: a second service on a second platform to reach your database, with no JDBC and therefore no SQLDelight. Nonsensical for a self-hostable container. Skip.
  • rqlite — good software solving multi-node HA, which you don't have. Self-hosters would need a cluster. Skip — but it's the right answer if this ever goes multi-node.
  • DuckDB — categorically wrong tool. It's OLAP: columnar, built to scan millions of rows for aggregates. You're OLTP: point lookups, single-row writes, transactions. It also has worse write concurrency than SQLite. It's what you'd use to analyse a dump of your tracker, not run it.
  • Managed Postgres — Neon's free tier is the best of them (0.5 GB, scale-to-zero, no overage billing). Supabase pauses projects after 7 days of database inactivity, which is a live landmine for a quiet internal tracker. Railway's own Postgres is not a managed service — their docs call it an unmanaged Postgres Docker image, no HA, no managed backups, no PITR. Fine, but know what it is. The deeper point: managed Postgres is not a self-hosting story. You can't ask someone deploying your container to go sign up for Neon.

Kotlin data access, and the dual-dialect trap

SQLDelight 2.3.2, SQLite dialect, JVM target. You already run 2.0.2 in Lunamux and darknessirc, so this is a minor bump on a tool you know. It's the only KMP-capable option here, so "share schema types with a client later" stays free. Its migrations are its quiet superpower: numbered .sqm files plus a Gradle verifyMigrations task that fails your build if the migrations don't produce the schema your .sq files declare. That's compile-time protection against schema drift, which neither Exposed nor Flyway gives you. You don't need Flyway at all initially.

Pin 2.3.2 exactly — 2.2.0, 2.3.0 and 2.3.1 are all marked failed releases with partially-published artifacts. Don't use a version range.

Exposed hit 1.0 in January 2026 and is moving fast (1.3.1 in July), which is a genuine change if you evaluated it a year ago — but it's JVM-only, so it's out on KMP grounds, and its createMissingTablesAndColumns() is best-effort DDL reconciliation rather than versioned migration. jOOQ is the most powerful option and its Apache-2.0 edition covers SQLite and Postgres both, but it's JVM-only and Java-first.

On shipping both SQLite and Postgres so self-hosters can pick

It's a trap at this stage, and the reason is concrete rather than aesthetic. SQLDelight generates against a dialect, and the generated Kotlin types differ: SQLite has no native BOOLEAN, no TIMESTAMP, no UUID, and INTEGER PRIMARY KEY vs BIGSERIAL generate different code. Then the semantics diverge — type affinity, date handling, transaction isolation, full-text search (FTS5 vs tsvector is a total rewrite). The cost isn't writing it once; it's that you must run your whole test suite against both, forever, or the second backend silently rots.

Instead: SQLite only, all data access behind a repository interface, and keep the SQL boring — no FTS5, timestamps as epoch-millis INTEGER, UUIDs as TEXT. Then a Postgres implementation is additive if anyone ever asks. Vaultwarden's audience dwarfs yours and still defaults to SQLite. Nobody self-hosting an issue tracker for tens of users needs Postgres.

07Scaling & instances

Placed here because the constraint originates in the previous section: SQLite decides this.

One instance

You won't need multiple instances — and with SQLite you can't have them. Railway enforces the same limit independently: "Replicas cannot be used with volumes." So this isn't a knob you can turn and get wrong. The real questions are whether you'd ever want to, and what the exit looks like.

Would you ever need to? The numbers aren't close

  • Railway Hobby scales one service to 48 GB RAM and 48 vCPU. That's a large machine, and it's a slider — not an architecture change.
  • A Ktor/Netty app on 1 vCPU and 512 MB handles hundreds of requests per second for this workload.
  • An issue tracker for tens of users is a few requests per second at peak, overwhelmingly reads.
  • SQLite's own guidance puts the threshold near 100k hits/day; sqlite.org serves 400–500k requests/day on it.

You'd hit thousands of concurrent users before one instance was the constraint, and you'd see it coming in CPU and p99 latency. Vertical scaling is the answer, and it's a slider you probably never touch.

What one instance actually costs you

Two things — and you pay both regardless of replicas, because the volume constraint already imposes them:

  • No high availability. If the container dies you're down until it restarts. Worse, Railway healthchecks run at deploy time only, so a JVM that deadlocks at 3am stays deadlocked until you notice. Point an external uptime check at /health.
  • Deploys have downtime — a few seconds while the old container releases the volume and the new one mounts it. Railway won't let two deployments mount one volume, so healthchecks can't hand over cleanly.

Both are fine for an issue tracker and neither would be for something with an SLA. Know which you're building.

What would break if you went multi-instance

More than just the database — and one of them is a security regression rather than a performance one:

One thing you already got right

The stateless AES-GCM session token from FramnaFolk (§3) means no session table and no sticky sessions — any instance can validate any request, because the session is self-contained in the encrypted cookie. That's the piece that usually forces sticky load balancing or a Redis session store. A nice accident of following your own precedent.

Why SQLite is a hard stop, not a limitation to engineer around

Worth understanding the mechanism. Postgres is a server: your app opens a TCP connection and the server arbitrates concurrent access across every client, wherever they are. SQLite is a library compiled into your process: your app opens a file, and coordination happens through filesystem locks.

Filesystem locks only work between processes on the same machine, on a real local filesystem. Two Railway replicas are two machines. There is no lock they can share. And the network-filesystem workaround is the dangerous one, per §6 — NFS/EFS emulate locking well enough to appear to work, so both instances believe they hold the write lock and you get silent corruption instead of an error. Railway forbidding the combination is them saving you from it.

The exit, if you ever need it

This is the concrete payoff for the repository interface in §6, which otherwise sounds like generic hygiene:

  1. Write a Postgres implementation of the repository interface — bounded work, confined to the data layer, if you kept the SQL boring (no FTS5, epoch-millis timestamps, UUIDs as TEXT).
  2. Move rate limiter state into the database. Small, and worth doing anyway.
  3. Drop Litestream — Postgres has its own backup story.
  4. Add a DB lock for scheduled jobs.
  5. Turn up replicas. Sessions already work; nothing else is stateful.

Roughly a week — spent once you have traffic to justify it, on a schema that's stopped moving. Doing it now costs the same week plus the permanent dual-dialect test matrix (§6), to solve a problem you don't have.

Cheaper levers, in the order you'd reach for them

1. Vertical scale — a slider. Covers you to thousands of users.
2. Cloudflare cache in front of anonymous/public issue views. If a project's issues are publicly readable, that's your read traffic gone at the edge, free, without touching the app.
3. Then, and only then, Postgres + replicas.

Most projects that "need to scale" needed step 2.

Recommendation: one instance, vertical scaling, don't design for horizontal. Keep the repository interface and keep the SQL portable — an afternoon of discipline now, and it's the entire migration path later. Revisit on evidence, not vibes. And for an open-source self-hosted tracker, "runs as exactly one instance" is unremarkable: Vaultwarden, Gitea-on-SQLite and Miniflux are all the same shape. Nobody will file an issue about it.

08Email: sending & receiving

Your specific question — can Gmail still impersonate lunamux.dev? — has a yes, with one condition.

The mechanism, in one paragraph

You never run an SMTP server, and your Ktor code never speaks SMTP. Two vendors handle two independent directions. Inbound: Cloudflare hosts real receiving SMTP servers (that's what the route1/2/3.mx.cloudflare.net MX records point at), which accept mail for lunamux.dev and forward it to your Gmail. Your server isn't in that path at all. Outbound: your server makes an ordinary HTTPS POST to Resend's REST API; Resend's mail servers do the SMTP delivery, signing with your DKIM key. Replies from Gmail: Gmail acts as an SMTP client, relaying through smtp.resend.com:587 — that's what the "outbound gateway" toggle permits.

Running your own SMTP is not a realistic option, and not mainly for reputation reasons: Railway and every major cloud block outbound port 25 by default, and you can't set the reverse-DNS record receivers demand because you don't own the IP. See answers.html §1 for the full flow diagrams.

Sending verification mail: Resend

You POST JSON to their API; they handle SMTP delivery, DKIM signing, bounce handling, suppression lists and deliverability. Under the hood they run on Amazon SES, which is why the DNS records they hand you point at amazonses.com. You're paying them (nothing) to abstract the part of email that is genuinely a specialty.

Receiving lunamux.dev mail: Cloudflare Email Routing

Your actual question: can Gmail send as lunamux.dev?

Yes

Gmail allows up to 99 "Send mail as" addresses and does not check domain ownership — it checks control of the mailbox, by emailing a confirmation code. Cloudflare Email Routing delivers that code to your Gmail. The condition: for a domain Google can't verify you own, you must supply SMTP credentials. There is no "send through Gmail's servers" option.

That option was withdrawn for non-Google-hosted addresses around 2014, and for good reason: mail sent that way has From: you@lunamux.dev but a gmail.com Return-Path and DKIM, so neither aligns and DMARC fails on anything stricter than p=none. Outlook renders it as "From you@gmail.com on behalf of you@lunamux.dev". Routing through Resend's SMTP instead gives you DKIM signed with d=lunamux.dev, which aligns and passes DMARC cleanly.

The Workspace-specific gotcha that will bite you

Because soderbjorn.se is Workspace, not consumer Gmail, the SMTP fields are rejected with a "Functionality not enabled" error until an admin turns on Admin console → Apps → Google Workspace → Gmail → End User Access → Allow per-user outbound gateways. You're the admin, so it's self-serve — but propagation can take up to 24 hours, and the error message doesn't tell you this is what's wrong.

The recipe

  1. Cloudflare Email Routing on lunamux.dev → destination = your soderbjorn.se Gmail → verify → catch-all rule.
  2. Resend: verify send.lunamux.dev (SPF + DKIM), take the SMTP credentials.
  3. Admin console: enable per-user outbound gateways.
  4. Gmail → Settings → Accounts → Send mail as → add hello@lunamux.dev → SMTP smtp.resend.com, port 587, TLS, username resend, password = API key.
  5. Confirmation code arrives via Cloudflare. Paste. Done.

The alternative: a Workspace domain alias

Worth knowing because it's strictly simpler if the constraint fits. A domain alias is free (up to 20), needs no extra licences, and gives you full send and receive as robert@lunamux.dev through Google's own servers with Google-managed DKIM — no relay, no SMTP config, no "via" banner. A secondary domain is different: it has its own separate users, and each consumes a paid licence.

The catch is exactly what you suspected: an alias domain mirrors existing usernames. robert@soderbjorn.se becomes robert@lunamux.dev, forced. You cannot create hello@lunamux.dev or support@lunamux.dev unless a matching user exists on soderbjorn.se. Local parts are welded together.

These two paths are mutually exclusive

A domain has exactly one MX set, and both want it. Cloudflare Email Routing replaces and locks the MX records — while it manages the zone you can't add or modify MX at all. To point MX at Google you must disable Email Routing first. So: catch-all and arbitrary addresses (Cloudflare) or Google-native alias with mirrored usernames. Not both.

But note the transactional half is independent. Resend on send.lunamux.dev is a subdomain and doesn't touch the root MX — so you can run the Workspace alias for your mailbox and Resend for the server's verification mail simultaneously. That's arguably the best combination, at the price of giving up catch-all.

My recommendation: Cloudflare Email Routing. You'll want hello@, support@, noreply@ and dmarc@ on a product domain, and the alias path can't give you any of them. The extra machinery is one admin toggle and one SMTP config.

DNS records

Use a sending subdomain. Three reasons: a brand-new root domain has no sending reputation, so if verification mail gets spam-flagged the damage is confined to send.lunamux.dev; it keeps the root's MX free for Cloudflare; and relaxed DMARC alignment (the default) covers it since both share an organisational domain.

# inbound — Cloudflare Email Routing provisions these on the root
MX   lunamux.dev            route1.mx.cloudflare.net   # priorities are randomised per
MX   lunamux.dev            route2.mx.cloudflare.net   # zone — read the dashboard,
MX   lunamux.dev            route3.mx.cloudflare.net   # don't hardcode. DNS-only (grey).
TXT  lunamux.dev            "v=spf1 include:_spf.mx.cloudflare.net ~all"
TXT  cf2024-1._domainkey.lunamux.dev    [key from dashboard]

# outbound — on the sending subdomain (Resend)
MX   send.lunamux.dev       feedback-smtp.eu-west-1.amazonses.com   10
TXT  send.lunamux.dev       "v=spf1 include:amazonses.com ~all"
TXT  resend._domainkey.send.lunamux.dev  "p=MIGfMA0GCSqGSIb3DQ..."

# DMARC — start permissive, tighten after ~2 weeks of clean reports
TXT  _dmarc.lunamux.dev
     "v=DMARC1; p=none; rua=mailto:dmarc@lunamux.dev; fo=1; adkim=r; aspf=r"
     # → p=quarantine → p=reject

Why alignment matters: DMARC passes only if the From: header domain matches the domain that passed SPF or DKIM. Authentication alone isn't enough — this is the source of every "SPF and DKIM both pass but DMARC fails" confusion. You only need one aligned, and with a relay it'll be DKIM, because the Return-Path belongs to the relay. Keep relaxed alignment (adkim=r) — strict alignment plus a sending subdomain is a common self-inflicted failure.

Two SPF rules that bite: one SPF record per domain, ever — two v=spf1 TXT records is a permerror and SPF fails entirely. And there's a 10-DNS-lookup limit; the subdomain split helps, since the root carries only Cloudflare's include and the subdomain only Resend's.

Point rua at an address Cloudflare forwards to you, and expect some initial spam-foldering regardless — it improves with engagement. Keep the mail plain: minimal HTML, no tracking pixels, no link shorteners, a real Reply-To.

Abuse — the thing that turns email into a bill

You flagged surprise bills from traffic; the realistic vector isn't traffic, it's your signup endpoint. Email bombing: an attacker POSTs /signup repeatedly with a victim's address, and your server dutifully mails someone who never signed up. You become the abuse vector, and your domain reputation and Resend account pay for it. Or they simply burn your 3 000/month in minutes to deny real signups.

Layer these — none is sufficient alone:

  • Rate limit per target email address (e.g. 3 sends/24h), not just per IP. This is the one that actually stops email bombing — the victim's address is the constant across distributed sources, while IPs are not.
  • Rate limit per IP too (5 signups/hour) — cheap, catches naive floods.
  • Cloudflare Turnstile on the form. It's free, you're already on Cloudflare. Verify the token server-side in Ktor — a client-side widget alone is bypassed by POSTing the endpoint directly.
  • A hard daily send cap in your own code. A counter that refuses to call Resend past ~200/day. Resend's 429 protects your wallet; this protects your reputation and keeps real signups working.
  • Don't leak account existence — same response whether the address is new or known.

Two notes from reading your CSS:

  • Name the variables semantically this time. Your site carries --green holding #4dc8f5, with a comment explaining the names are historical and kept so existing usages pick up the new colours. That was the right call for a rename in place, but don't inherit it — a tenant theming their tracker shouldn't have to set a variable called --green to a shade of orange.
  • #eaf3fb appears 16 times un-tokenised in styles.css as the mint-white heading colour. If the tracker's palette is going to track the site's, tokenise that one (as --head above) rather than copying the literal across.

How the theme should get in

Server-side, from the project's entry in projects.yaml (§2), emitted as a :root block into the embed page's <head>. Not via query parameters — an attacker could then restyle your tracker arbitrarily on a page they control, which is a phishing surface. Not via postMessage from the parent either, for the same reason plus a flash of unstyled content on every load.

Validate the colour values server-side before emitting them into CSS. A theme field is a string that lands in a <style> block — treat it as untrusted input, parse it as a colour, and reject anything that isn't one. Emitting user-supplied strings into CSS unescaped is a real injection vector, not a theoretical one.

For fonts: your site is monospace-only via system fonts with no @font-face and no webfont link — nothing to download, nothing to configure. Keep that property in the tracker; it's a meaningful chunk of why the site feels fast, and an embedded iframe pulling webfonts would undo it.

Lastly — don't port the CRT scanline overlay into the tracker. Your site already suppresses it over the live demo via body.demo-active, which tells you it's wrong over interactive content. Let the iframe be a clean surface inside the themed page.

11Docker & open source

Your instinct — a Docker component others can deploy — is sound, and there's a well-trodden shape for it.

The image

Multi-stage Gradle build. The thing that actually matters is caching the dependency resolution layer separately from the source, or every build re-downloads the world:

FROM eclipse-temurin:21-jdk AS build
WORKDIR /src
COPY gradle/ gradle/
COPY gradlew settings.gradle.kts build.gradle.kts ./
RUN ./gradlew --no-daemon dependencies      # cached unless deps change
COPY . .
RUN ./gradlew --no-daemon installDist

FROM eclipse-temurin:21-jre-alpine
COPY --from=build /src/build/install/app /app
ENV DATABASE_PATH=/data/app.db
VOLUME /data
EXPOSE 8080
ENTRYPOINT ["/app/bin/app"]

Size expectations, and be sceptical of blog numbers — measure yours. A Temurin JRE plus fat jar lands around 250–350 MB; jre-alpine multi-stage around 120–180 MB; jlink + distroless around 80–120 MB. Reported 339 MB → 54 MB reductions are for trivial apps, not Ktor + Netty + SQLDelight.

Start with jre-alpine; add jlink only if size actually bothers you. jlink adds real friction — jdeps misses reflective and ServiceLoader dependencies, so you'll chase NoClassDefFoundError at runtime and hand-add --add-modules java.naming,jdk.crypto.ec,…. Not a good use of your first week.

The one that will actually bite you

xerial's sqlite-jdbc ships a native .so and needs the musl vs glibc build to match. Alpine is musl; recent xerial versions handle it, but this is the classic "works on my Mac, UnsatisfiedLinkError in production". Test it on both amd64 and arm64 before you commit to a base image. distroless/base-debian12 (glibc) sidesteps it if you hit trouble.

Also: build multi-arch (linux/amd64,linux/arm64 via buildx). A large share of self-hosters are on a Raspberry Pi or an ARM VPS, and missing arm64 is the number-one open-source packaging complaint. And set -XX:MaxRAMPercentage=75 or the JVM may read the host's memory rather than the container limit.

Configuration

You asked how users would configure it alongside the container. Environment variables for scalars, plus exactly one mounted config file for the project list. Env vars compose natively with docker-compose, Kubernetes, Railway and Fly, and a mounted file requires the user to create it, mount it and debug the mount — so keep files to the one case that genuinely needs structure. That's projects.yaml (§2): a nested list of projects with themes and origin allowlists is not a scalar, and cramming it into an env var is clever for a week and miserable forever. Everything else — DATABASE_PATH, MAIL_FROM, RESEND_API_KEY, BASE_URL — is an env var.

The pattern that works:

  • Every setting has a sane default. docker run -v data:/data -p 8080:8080 ghcr.io/you/tracker should just work with zero config.
  • Ship a .env.example documenting every variable with comments. This is the single most useful file in Vaultwarden's repo.
  • Support *_FILE variants for secrets (RESEND_API_KEY_FILE=/run/secrets/resend) — Docker and Kubernetes mount secrets as files, and env vars leak via docker inspect and crash dumps.
  • Validate at startup and fail loudly. Never silently default a misconfigured value. Vaultwarden has a live bug of exactly this class — a bad DATABASE_URL silently creates an empty SQLite file, and the user finds out when their data is "gone". Learn from it for free.

Ktor note: application.conf with ${?ENV_VAR} substitution is a nice middle ground — the schema stays visible in-repo while remaining env-injectable.

The precedent to copy

Vaultwarden is the closest model to what you're building and worth studying directly: single container, SQLite by default via DATABASE_URL=sqlite://data/db.sqlite3, with Postgres and MySQL as opt-in through the same variable, ~50 MB RAM idle, one volume at /data. Gitea does the same — SQLite default, Postgres optional, compose file ships with the Postgres service commented out. Both have far more write concurrency than you will and still default to SQLite.

The counterexamples are instructive too: Miniflux is Postgres-only by deliberate choice — one backend, one test matrix — which is legitimate but forces every self-hoster to run two containers. Plausible needs Postgres and ClickHouse, and their self-hosting support burden is correspondingly heavy. Don't emulate that.

The pattern is unambiguous: small data + few writers → SQLite by default, Postgres as an escape hatch. An issue tracker for tens of users is squarely in that category. Ship a docker-compose.yml at the repo root that works with docker compose up -d and no edits, with Litestream commented out as opt-in.

On open-sourcing it

The single-operator model (§2) makes this lower-risk than I'd first framed it: you're shipping software, not operating a platform. Nobody else's projects live on your server, so open-sourcing doesn't sign you up for other people's abuse, moderation or outages. The residual cost is ordinary maintainership — issues, PRs, "does it support LDAP", and a stranger's misconfiguration becoming your Saturday.

Timing still matters, since open-sourcing later is easy and the reverse isn't. Lunamux is MIT with a NOTICE file, so you have a precedent. My suggestion: build it private, deploy it for Lunamux, and open it once projects.yaml has actually been exercised by a second project — that's the point at which the config surface has stopped moving, which is what makes a self-hostable release honest rather than aspirational.

13Suggested order of work

Sequenced to hit the risky, un-de-riskable things first.

The ordering principle: the two things that could invalidate the design are the Kotlin/JS production bundle and Google OAuth inside the frame. Both are cheap to test in isolation and expensive to discover late. Do them before you write an issue tracker.

  1. Spike the embed + auth path, with nothing in it. A Ktor server on Railway serving one Kotlin/JS page that says "hello", framed on a local copy of lunamux-web, with Google sign-in via initCodeClient popup and a session cookie round-tripping. Build it with jsBrowserProductionWebpack from the first commit so you find out immediately whether the name-mangling bug that forced Lunamux to ship dev bundles affects you too. If both work, everything else here is ordinary work.
  2. Set the Railway hard limit. Before you deploy anything real. Thirty seconds, and it's the requirement you were most worried about.
  3. Wire the volume and prove persistence. Write a row, redeploy, read it back. Assert at startup that /data is a different device than /. Get Litestream replicating to R2 and — this is the part everyone skips — do a restore. A backup you've never restored is a hypothesis.
  4. Email, end to end. Cloudflare Email Routing → Gmail, Resend on send.lunamux.dev, DMARC at p=none, send yourself a verification link. Then the Gmail "Send mail as" setup — and remember the per-user-outbound-gateways toggle can take a day to propagate, so start it early rather than debugging it under pressure.
  5. Now build the tracker. Schema with project_id and per-project issue numbers from the first migration. Rate limits on the signup endpoint in the same commit as the signup endpoint, not later.
  6. Second project, even a fake one. The multi-project design isn't proven until something other than Lunamux uses it — that's when you find out whether the CNAME flow, the origin allowlist and the theme records actually hold together.
  7. Open source it once the config surface has stopped moving.

Things I'd flag as genuinely uncertain

Everything above is sourced from current vendor documentation, but these specifically are worth re-checking at decision time rather than trusting me:

  • Railway's domains-per-service limit — their limits reference page 404s. This matters if the per-project CNAME plan scales beyond a handful.
  • Railway prepaid credit — whether it still exists (see §12).
  • Whether Railway's Serverless actually zeroes billing — the docs frame it as cost reduction but don't say so plainly. Moot if you take my advice and don't rely on it.
  • Firefox's FedCM support state — it was in flight through 2025–26. Affects One Tap in the frame, not the popup path.
  • xerial sqlite-jdbc on musl/arm64 — the most likely concrete packaging failure. Test, don't assume.
  • Litestream on Railway specifically — the sidecar pattern its docs recommend assumes two containers sharing a volume, which Railway's per-service volumes make awkward. The -exec single-container form should work, but I'd verify it rather than take it on faith.
