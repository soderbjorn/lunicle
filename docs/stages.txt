Stage 1 — done, validated in production 2026-07-16

Embed loads on lunamux.dev in Chrome and Safari, counter intact, served from Railway.

A POC which has the following:
* A Kotlin multiplatform project with a server and a UI (the server serving the UI), with them sharing code for the API between them, and the UI using Kotlin DOM APIs (like FramnaFolk does) to produce code in a theme styled liked the Lunamux website. The view using Kotlin DOM APIs has a BackingViewModel on the Kotlin side which serves as its view model. The view has a button and a counter display.
* The backing view model stores the counter in memory which is incremented by call from the view when the button is pressed.
* A StateFlow is emitted with a single state for the entire view. The UI listens and updates the counter display.
* No persistence, no database.
* Everything packaged to a Docker container I can deploy on Railway.
* Destination: a subdomain "lunicle.lunamux.dev" on the Lunamux website. Secret for now, no links to it.
* An instructions HTML with step-by-step instructions how to configure the domain, how to configure Railway and deploy the Docker file there.

Watch out: Google's consent endpoint sends X-Frame-Options: DENY and can never be framed.
The popup flow is the only path. Test sign-in through the iframe from the first commit —
testing it at lunicle.lunamux.dev directly passes and proves nothing.

Watch out: a Railway volume mounts owned by root, and this container runs as an
unprivileged user — so the server cannot write its own database, and SQLite says only
"unable to open database file". Railway's documented answer is RAILWAY_RUN_UID=0, i.e.
run everything as root, which throws the non-root user away. scripts/container-entrypoint.sh
instead chowns the mount as root and drops to uid 10001 before exec'ing the JVM. Do not set
RAILWAY_RUN_UID; it undoes this.

Decisions taken during the persistence half, worth not re-litigating:

* SQLDelight, in :server only. SQL-first rather than an ORM, and it brings migrations,
  which the volume makes mandatory from the first deploy. Its multiplatform half is
  unused on purpose: the client never touches the database — it cannot, the file is on
  Railway's disk — and reaches it only through LunicleApi over HTTP.
* Sessions persist too, not just users and counters. Sessions.kt had promised this
  ("when the volume lands, this file is what gets replaced"). A redeploy no longer signs
  anyone out, which is a stronger result than the exit criterion asks for.
* The counter is keyed by user id, so it follows the person rather than the browser.
  Signed out, the panel shows the counter dimmed and inert with "Sign in to start
  counting" — the affordance explaining itself — rather than hiding it or keeping a
  shared anonymous count.
* /api/counter now 401s when signed out. /api/session never does, and is therefore what
  the dev scripts probe for liveness.

Exit criterion, still outstanding: run it in production, through the iframe on lunamux.dev.
Proven locally against a real root-owned Docker volume — new container, same volume, count
and session both intact — which is the same mechanism but not the same proof.
