Stage 2 — OAuth provider setup

The steps that need your accounts: a Google Cloud project, two GitHub OAuth apps, and one header on the parent site. Everything here is configuration you do in a browser — no code. Do this first; the sign-in code is written against the values it produces.

Read first The shape of the problem

Two paragraphs that explain every strange decision below.

Neither provider can be framed. Verified live, today, against both:

$ curl -sSI "https://accounts.google.com/o/oauth2/v2/auth?client_id=…"
HTTP/2 302
x-frame-options: DENY

$ curl -sSI "https://github.com/login/oauth/authorize?client_id=test"
HTTP/2 302
x-frame-options: deny
content-security-policy: … frame-ancestors 'none'; …

GitHub is double-blocked — the legacy header and CSP. There is no header you can set on your side to change either. A full-page redirect inside the iframe is equally dead: it would navigate the frame to the provider, and the provider refuses to be the thing in a frame. So the flow is a popup, for both providers, and that is not a preference.

Lunicle is a framed document, and that changes which headers matter. Almost every OAuth guide you'll find assumes your app is the top-level page. Yours isn't — it's an iframe inside lunamux.dev. The consequence is the single most surprising thing in this document, and it has its own section (Step 4).

What you'll produce

Four secrets and two client ids, which become environment variables on Railway and a local .env for development. Nothing in this document goes into git.

Errata Two things stages.html gets wrong

Corrected here rather than silently contradicted. The plan was written before the providers were checked.

"Cross-Origin-Opener-Policy: same-origin-allow-popups on your server"

This is a no-op and will not help you. COOP is only enforced on top-level browsing contexts. Lunicle is served into an iframe, so a COOP header on lunicle.lunamux.dev is read and ignored by the browser. Setting it costs nothing and achieves nothing.

The COOP that can actually break your sign-in is on lunamux.dev, the parent — and the failure is the one the plan describes, so the instinct was right and only the address was wrong. See Step 4.

"needs allow='identity-credentials-get' on the iframe element"

Not for this flow, as far as the documentation goes. That attribute gates FedCM — One Tap and the Sign In With Google button, which go through navigator.credentials.get(). The popup we're using (initCodeClient) is window.open-based and shouldn't need it.

Add it anyway. It is inert when unused, and Google has been migrating GIS surfaces onto FedCM since 2025 with no published statement about whether the code client follows. Cheap insurance against a silent breakage later.

Step 1 Google — the OAuth client

The console was reorganised; the path in most tutorials is stale.

  1. Go to console.cloud.google.com/auth/clients — that's Google Auth Platform → Clients. The old APIs & Services → Credentials route still redirects here, which is why both names are floating around.
  2. Create a project (or pick one). If the app isn't registered yet, Google forces you through branding registration first — do that, it's Step 2 below.
  3. Create client → application type Web application.
  4. Name it something you'll recognise in a year. Lunicle is fine.
  5. Fill both origin fields exactly as in the table, then Create.
FieldValues
Authorized JavaScript origins https://lunicle.lunamux.dev
http://localhost:8080
http://localhost
Authorized redirect URIs https://lunicle.lunamux.dev
http://localhost:8080

Yes, the redirect URIs really are bare origins — and yes, that looks wrong

In popup mode you never set a redirect_uri; you pass a callback function. Google's JS reference is explicit: "When ux_mode: 'popup' is used this parameter is ignored and redirect_uri defaults to the origin of the page that calls initCodeClient." But the server-side token exchange still sends a redirect_uri, and that step's docs say it must be one of the URIs registered in the console. Its value is the origin. Hence: register the origin in both fields.

Flagging honest uncertainty: Google's own docs are in tension here — the popup page implies no redirect registration is needed, the exchange page implies it is. Registering in both fields costs nothing and satisfies both readings, which is why this document tells you to. If the exchange still rejects it, the community fallback is redirect_uri=postmessage, a gapi.auth2-era convention that appears in no current official documentation. Try the documented thing first.

Copy the Client ID and Client secret now. The secret is retrievable later, but not conveniently.

Before you debug a redirect_uri_mismatch, wait

The console warns that changes take five minutes to a few hours to propagate. A mismatch error on a config you just saved is usually not a mistake, it's a clock. Change one thing, wait, retry — rather than changing five things in the five minutes it takes to start working anyway.

Step 2 Google — audience, and why to publish immediately

Google Auth Platform → Branding / Audience / Data Access.

  1. Audience: External. Internal only exists for projects inside a Google Workspace organisation and restricts sign-in to that org's members. Your soderbjorn.se Workspace doesn't make lunamux.dev internal; anyone outside gets an org_internal error.
  2. Branding: app name, user support email, developer contact email. That's all Testing status requires.
  3. Data Access → scopes: openid, email, profile. Nothing else. These are non-sensitive, which is the entire reason Step 4 of this list is painless.
  4. Add yourself as a test user on the Audience page.
  5. Then publish to production. Yes, already.

Testing status expires tokens after seven days

Google: "Authorizations by a test user will expire seven days from the time of consent." A refresh token issued under Testing dies in a week and comes back as invalid_grant. You will have forgotten this configuration by then, and the bug presents as "sign-in worked fine last week and is broken now" — which is about the worst debugging prompt there is.

Testing also caps you at 100 test users, each added by hand.

Publishing removes both. And because you're only asking for openid email profile — all non-sensitive — publishing needs no verification review. There's no security questionnaire, no demo video, no waiting. The cap and the expiry just go away. This is the rare case where the scary-sounding button is the easy path, and taking it on day one saves you a mystery on day eight.

Step 3 GitHub — two OAuth apps

Two, because GitHub gives you no choice.

Path: your avatar → Settings → Developer settings (bottom of the left sidebar) → OAuth Apps → New OAuth App. Direct: github.com/settings/developers.

OAuth App, not GitHub App

GitHub's docs push GitHub Apps as the modern choice, and for repository access they're right — fine-grained permissions, short-lived tokens. None of that reasoning applies to you: you want identity and nothing else, touch no repositories, and a GitHub App would add an installation step and a permission prompt for zero benefit. OAuth App is correct here.

Create two. An OAuth App has exactly one callback URL — GitHub's docs state it plainly: "OAuth apps cannot have multiple callback URLs, unlike GitHub Apps." Host and port must match exactly, so no single registration can cover both production and localhost.

AppHomepage URLAuthorization callback URL
Lunicle https://lunicle.lunamux.dev https://lunicle.lunamux.dev/auth/github/callback
Lunicle (dev) http://localhost:8080 http://localhost:8080/auth/github/callback

Copy both client ids and generate a client secret for each — four values. The dev app's secret protects nothing of consequence, but keep it out of git anyway; the habit is the point.

The tempting third option is an open redirect

You'll find advice suggesting one app whose callback points at production, which then bounces the browser onward to localhost. That is an open-redirect shape wearing a convenience costume: a production endpoint that forwards an authorization code to wherever a parameter tells it to. Two apps and an environment switch is less clever and correct.

Scopes

read:user user:email. The second one is not optional and the reason is a trap: GET /user returns email: null whenever the user's address is private, which is extremely common and will absolutely be true of some early user while it isn't of you. The addresses live behind GET /user/emails, which requires user:email; take the entry that is both primary and verified. read:user alone does not grant emails.

Use state, and use PKCE (code_challenge + code_challenge_method=S256) — GitHub documents it for OAuth Apps now and marks it strongly recommended. It's a recent enough addition that older tutorials won't mention it.

Step 4 The parent site — the one that will bite

Two changes in lunamux-web. This is the step with no error message.

Everything so far was provider configuration. This step is about the page doing the framing, and it's where a correctly-configured sign-in still silently does nothing.

lunamux.dev must not send Cross-Origin-Opener-Policy: same-origin

When a top-level page sets COOP: same-origin and a cross-origin iframe inside it opens a popup, the browser forces noopener and puts the popup in a separate browsing context group. The popup opens. The user signs in. The popup closes. The callback never fires. Nothing appears in the console, because nothing went wrong from the browser's point of view — it did exactly what the header asked.

Checked on 2026-07-16: you are currently fine. GitHub Pages sends no COOP header at all, which is the safe default (unsafe-none):

$ curl -sD - -o /dev/null https://lunamux.dev/ | grep -i cross-origin
(nothing)

So this is a hazard to preserve, not one to fix. Nothing to do today — but it's a header you can't set on GitHub Pages anyway, which means the day this breaks is the day you move the parent site somewhere you can (Railway, Cloudflare Pages), and set security headers wholesale without noticing this one is load-bearing. If you ever add COOP, the value is same-origin-allow-popups.

Uncertainty, stated plainly: this nested-iframe COOP behaviour comes from a WHATWG spec issue and MDN, not from Google's documentation, and this corner of the spec has been moving — restrict-properties and friends are recent. Treat it as the first thing to suspect if the popup goes quiet, not as settled law.

Second change: add the FedCM attribute to the iframe element, per the Errata reasoning above.

<iframe id="issues-iframe" title="Lunamux issues"
        allow="identity-credentials-get"
        data-src="https://lunicle.lunamux.dev/"></iframe>

If the frame is ever nested further, every ancestor iframe needs it too — Google's docs are explicit that it must be on all parent iframes. Not your situation today.

Step 5 Where the secrets go

Railway variables for production, a gitignored file for local.

Four values. The server reads them from the environment, the same way it already reads PORT and FRAME_ANCESTORS.

VariableProduction (Railway)Local
GOOGLE_CLIENT_IDfrom Step 1same — one Google client covers both
GOOGLE_CLIENT_SECRETfrom Step 1same
GITHUB_CLIENT_IDthe Lunicle appthe Lunicle (dev) app
GITHUB_CLIENT_SECRETthe Lunicle appthe Lunicle (dev) app

Railway → your service → Variables. Setting a variable triggers a redeploy; that's expected and, at this stage, free of consequence.

The client secret never reaches the browser

The client id is public by design and ships in the bundle. The secret is used in exactly one place — the server-side POST that exchanges the code for a token. If a secret ever appears in Kotlin/JS source, it is in the bundle, and the bundle is a file anyone can download from lunicle.lunamux.dev. Both providers let you rotate; assume you'll need to.

Reference The exchange endpoints

For when the code is being written — and for the two gotchas.

Google

POST https://oauth2.googleapis.com/token
Content-Type: application/x-www-form-urlencoded

code=…&client_id=…&client_secret=…
&redirect_uri=<the calling page's origin>
&grant_type=authorization_code

Returns access_token, expires_in, scope, token_type, and — because openid is in scope — an id_token, which is where the identity actually is. A refresh_token only appears with access_type=offline, which sign-in doesn't need.

GitHub

POST https://github.com/login/oauth/access_token
Accept: application/json          ← without this you get a URL-encoded body

client_id=…&client_secret=…&code=…&redirect_uri=…&code_verifier=…

That Accept header is the classic one. Omit it and GitHub answers access_token=…&scope=… as form encoding, your JSON parser throws something unhelpful, and you go looking for the bug in your credentials.

Then GET https://api.github.com/user/emails for the verified primary address, per Step 3.

Done What you should have

  • A Google OAuth client, published to production, with three JS origins and two redirect URIs.
  • Two GitHub OAuth apps, prod and dev, each with its own secret.

  • lunamux.dev confirmed not to send COOP: same-origin, and its iframe carrying allow="identity-credentials-get".
