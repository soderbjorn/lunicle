SCOPE / v0

A simple issue tracker,
built for engineers.

Two lists below. The first is what you already asked for, fleshed out into concrete decisions you'll have to make anyway. The second is what a tracker needs before a real team will actually use it instead of quietly moving back to a spreadsheet.

What you asked for

Your original list, with the decisions each one implies.

TICKETS / CRUD

Create and edit tickets — the core loop everything else hangs off.

  • Human-readable key per ticket (PROJ-142) — never expose raw database ids, people paste keys into Slack and commit messages.
  • Title, markdown description, reporter, assignee, timestamps.
  • Issue type: bug, task, story, epic. Drives which fields show.
  • Status and resolution as separate fields — "Closed" and "Won't fix" answer different questions.
  • Priority and, for bugs, severity — impact and urgency aren't the same axis.
  • Soft delete only. Someone always deletes the wrong ticket.
USERS / ACCESS

Manage users and permissions without building an identity provider.

  • SSO from day one (OIDC / Google / GitHub). Don't own passwords if you can avoid it.
  • Roles scoped per project, not globally: admin, member, reporter, viewer.
  • Reporter-only role for support or external users who file but don't browse.
  • Teams/groups, so access is granted to a group rather than 30 individuals.
  • Deactivate, never delete, a user — their comment history has to survive.
  • Service accounts and API tokens for CI, bots, and scripts.
VERSIONS / RELEASES

Planned fix version vs. actual fixed version — two fields, deliberately.

  • Target version: intent. Set at triage, moves when plans slip.
  • Fixed version: fact. Set on merge/release, never edited afterward.
  • Keeping both is what lets you answer "what slipped out of 2.4?" — a single field silently overwrites that history.
  • Affects version(s): where the bug was seen. Multi-value.
  • Versions as real objects: name, release date, status (unreleased / released / archived).
  • Generate release notes from tickets whose fixed version equals the release.
BOARDS / KANBAN + SPRINTS

Both are board views over the same tickets. See the comparison below.

  • Columns map to workflow statuses; drag-drop is a status transition.
  • Swimlanes by assignee, epic, or priority.
  • WIP limits per column (kanban's whole point).
  • Sprints as first-class objects: name, goal, start/end, state.
  • Board mode is a project setting, not a fork of the codebase.
ATTACHMENTS

Engineers attach screenshots and logs constantly. Make it frictionless.

  • Paste-from-clipboard and drag-drop straight into the description or a comment.
  • Object storage (S3-compatible) with pre-signed URLs — never blobs in your database.
  • Inline image previews; syntax-highlighted preview for logs and diffs.
  • Size caps, MIME allowlist, and virus scanning if anything is user-facing.
  • Attachments inherit the ticket's permissions — a leaked URL is a data breach.
INLINE EDITING

Click a field, change it, done. No modal, no separate edit screen.

  • Optimistic UI with rollback on failure.
  • Conflict handling: version/etag per ticket so two editors don't clobber each other silently.
  • Every inline edit writes a history entry — cheap edits still need an audit trail.
  • Escape cancels, Cmd+Enter saves. Engineers live on the keyboard.
  • Same editing affordance in list, board, and detail views.

Kanban vs. sprints — how to differentiate

Don't build two products. Build one board and one backlog, then let a project setting decide whether work is bounded by a time box (sprint) or by a WIP limit (kanban). That single choice cascades into everything below.

Dimension Kanban Sprints (Scrum)
Unit of commitment None — pull the next card when there's capacity A fixed set of tickets committed to a dated iteration
What limits work WIP limit per column Sprint capacity in points or hours
Board contents Everything not done, continuously Only tickets in the active sprint
Backlog role An ordered queue you pull from A staging area you plan sprints out of
Cadence Continuous flow; release when ready Start → plan → work → close → retro, on a fixed rhythm
Key metric Cycle time, throughput, aging WIP Velocity, burndown, commitment accuracy
Leftover work Concept doesn't exist — it just stays in its column Explicitly rolled over into the next sprint at close
Best fit Support, ops, interrupt-driven teams Feature teams planning against a roadmap
THE SHARED MODEL

What both modes reduce to under the hood.

  • A ticket has a status and a rank (an orderable position).
  • A board is a saved filter + a column-to-status mapping.
  • Kanban = that board, with WIP limits, filtered to "not done".
  • Scrum = that board, filtered to sprint == active, plus a backlog view that assigns tickets to sprints.
  • A sprint is just a nullable foreign key on the ticket plus a small sprint table. That's the entire difference.
MY ADVICE / v0

Sequencing, if you want something usable in weeks not quarters.

  • Ship kanban first. It's strictly simpler and it's a coherent product on its own.
  • Add the sprint foreign key to your schema now even if the UI comes later — retrofitting it across a live board is miserable.
  • Resist per-project custom workflows in v0. It's the single biggest complexity multiplier in every tracker ever built.
  • One fixed workflow, one board, one backlog. Earn the configurability later.

Proposed additions

Everything below is missing from your list. The v0 items are, in my view, the ones you cannot credibly ship without — search and git integration especially. The later items are real but can wait.

SEARCH / FILTERINGv0

The single most-used feature in any tracker. Underbuild it and the tool is dead.

  • Full-text over title, description, and comments.
  • Structured filters: project, type, status, assignee, label, version, date ranges.
  • Saved filters, shareable by URL. "My open bugs" should be a link.
  • A small query language eventually (JQL-like) — but filters and URLs get you 90% there.
GIT / CI INTEGRATIONv0

This is what makes it a tracker for engineers rather than a todo list.

  • Detect the ticket key in branch names, commits, and PR titles; link automatically.
  • Show linked branches, PRs, and their CI status on the ticket.
  • Auto-transition on merge — the status update nobody remembers to do by hand.
  • Stamp fixed version from the release tag that contains the merge commit.
COMMENTS / ACTIVITYv0

Tickets are conversations. The history is often worth more than the ticket.

  • Markdown comments with code fences and @mentions.
  • Full change history: who changed what field, from what, to what, when.
  • Merged activity timeline — comments, transitions, and commits interleaved.
  • Internal vs. public comments if external reporters can see the ticket.
RELATIONSHIPSv0

Real work is a graph. Flat ticket lists lose the plot fast.

  • Parent/child: epic → story → subtask.
  • Links: blocks / blocked-by, duplicates, relates-to.
  • "Duplicate" needs to point at the canonical ticket, not just close.
  • Surface blockers on the board — a blocked card should look blocked.
NOTIFICATIONSv0

The feature most likely to make people mute your product. Tune it carefully.

  • Watchers per ticket; auto-watch on comment or assignment.
  • In-app inbox plus email; per-user granularity.
  • Batch and debounce — one digest, not nine emails from one bulk edit.
  • Slack/Teams delivery is usually more wanted than email.
API / WEBHOOKSv0

Engineers will automate this whether you plan for it or not.

  • REST API covering everything the UI can do — build the UI on it.
  • Token auth with scopes; rate limiting.
  • Outbound webhooks on create/update/transition.
  • CSV/JSON import and export. Nobody adopts a tracker they can't leave.
ORGANIZATIONv0

Structure that keeps a few thousand tickets navigable.

  • Projects with their own key, members, versions, and board.
  • Components or areas — "auth", "billing", "ios" — with default assignees.
  • Free-form labels alongside components; both, not either.
  • Due dates, and an explicit triage/backlog state for unsorted intake.
UX ESSENTIALSv0

The things that decide whether engineers actually keep tickets updated.

  • Keyboard shortcuts and a command palette. This audience expects it.
  • Bulk edit from the list view: reassign, relabel, move 40 tickets at once.
  • Ticket templates per type — a bug form that asks for repro steps and version.
  • Fast. Sub-100ms interactions or people go back to Slack threads.
REPORTINGlater

Deliberately deferred — but note which mode each metric belongs to.

  • Sprint mode: burndown, velocity over the last N sprints.
  • Kanban mode: cycle time, throughput, cumulative flow, aging WIP.
  • Estimation: story points or t-shirt sizes. Pick one, per project.
  • Roadmap view over epics and versions.
SCALE / MATURITYlater

Real needs that arrive with the second or third team.

  • Custom fields per project. Powerful, and a permanent complexity tax.
  • Configurable workflows with transition rules and required fields.
  • SLAs and escalation, if support ever files into this.
  • Time tracking. Ask whether you truly want it — it changes the culture.
  • Duplicate detection at file time; automation rules ("if X then Y").
NON-FUNCTIONALv0

Unglamorous, and the reason trackers get trusted or abandoned.

  • Backups you have actually restored from. Your tracker is institutional memory.
  • Audit log for permission and access changes.
  • Stable ticket URLs, forever. They get pasted into everything.
  • Responsive layout — triage happens on phones.
  • Dark mode. Non-negotiable for this audience.
