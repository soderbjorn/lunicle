Darkness Redesign — Analysis & Implementation Plan

Lunicle adopts the darkness toolkit shell · based on docs/darkness-redesign.txt incl. answers #1 and #2 · branch feature/darkness-migration · 2026-07-17

Goal & agreed decisions

Lunicle replaces its hand-written DOM UI (the web module) with the darkness-toolkit app shell, keeping the view-model layer (client) and everything below it. Toolkit changes are made opt-in so Lunamux's behaviour and appearance do not change.

  • Board lives in its own darkness window: opens maximised, minimizable, not closable. The single (invisible) tab uses the Auto layout preset.
  • Issues open in their own windows — read mode with an Edit button toggling edit mode (and back), permission-gated. Several may be open at once; reopening an issue focuses its existing window. New issue (from the + menu) is the same window starting in edit mode. Closing with unsaved changes → Save / Discard / Keep editing modal. No Cancel button.
  • + menu contains New issue and, when permitted, New project. New project opens a modal dialog (darkness-styled) with today's fields — removed from the board's project switcher.
  • Project switcher moves into the board window. Multiple projects supported.
  • Top bar: no sidebar (or its toggle), no world switcher, no tab strip, no 3D, no bell/info/cogwheel. Keeps +, window layout, dark/light cycle, theme sidebar, appearance sidebar, and Lunicle's sign-in/profile button trailing at the end.
  • Windows keep minimise/maximise/close only — no overflow menu (rename), no reformat.
  • Themes: the toolkit catalog, defaulting to Lunamux Dark. Theme and dark/light choice not persisted; window layout not persisted. Reload resets everything — acceptable for now.
  • Deep links (?issue=LMX-12) run normal init (board window) and additionally open the issue's window as if clicked.
  • Signed-out use keeps working: browse public projects, sign-in button in the top bar.
  • Board refresh: saving an issue (create or edit) triggers the board view model to refresh.
  • Restyle depth: board and issue content restyled to darkness/lunamux appearance as much as possible, not just the chrome.
  • Toolkit delivery: consumed like Lunamux — committed libs-repo pin + sibling composite-build auto-detect; toolkit's publishAllToLibsRepo gains Lunicle as a target. Work happens on the toolkit's main worktree; Lunamux compat verified by manual testing (I flag risks).

Survey findings (what exists today)

Lunicle (this repo)

  • UI is hand-written Kotlin/JS DOM in web/ — the throw-away layer (views, dialogs, Dom.kt, Icons.kt, MarkdownEditor UI, styles.css).
  • Keep layer is clean: client/viewmodel/ — one immutable State over a single StateFlow per VM, intent methods, no DOM/transport leakage. StorageRepository wraps the API. clientServer holds DTOs.
  • Key VMs: MainScreenBackingViewModel (board, picker, drag/drop, which dialog is open, deep links), IssueBackingViewModel, EditProjectBackingViewModel, SessionBackingViewModel, CommentBackingViewModel, ConnectionsBackingViewModel.
  • No unsaved-changes prompt today — a draft contract: New issue creates the DB row up-front (attachments need an owner); Cancel deletes the draft. The new Save/Discard maps onto this: Discard = delete draft (new) / drop local edits (existing).
  • Deep links (?project=, ?issue=) parsed in web/main.kt, resolved in StorageRepository.resolve(); URL written back via history.replaceState (iframe-friendly, no hash).
  • Permissions are server-decided affordances on DTOs (canCreateIssue, canEdit, canCreateProject, …) — already exactly what's needed to gate the Edit button and + menu items.
  • No local-lib plumbing (no libs-repo, no composite build) — must be added.

Lunamux (compatibility constraints)

  • Pins toolkit 0.2.31 from its committed libs-repo; sibling checkout auto-switches to composite build (darkness.toolkit.path, force-artifacts escape hatch). The toolkit's publishAllToLibsRepo targets lunamux + notegrow; Lunicle becomes a third target.
  • Lunamux queries toolkit-owned DOM in ~43 places (.dt-pane ×29, .dt-modal ×10, .dt-sidebar ×7), assumes the pane header wrapping structure, shadows the close action via action ordering, and sniffs theme-manager close via transitions. Rule for all toolkit changes: additive, opt-in, no CSS-class renames, no DOM restructuring in default configuration.

Implementation plan

Phase 1 — Toolkit: opt-in shell configurability

All in darkness-toolkit/main, every option defaulting to current behaviour:

  1. AppShellSpec.topbar (or similar) with flags: showSidebarToggle (false ⇒ sidebar fully absent), showTabStrip, plus explicit control over the built-in “New tab”/“New workspace” rows in the + menu (e.g. showNewTabMenuItem). Defaults = all current.
  2. Per-pane window chrome: a host hook (e.g. paneChrome(paneId): PaneChromeSpec) controlling closability per window; board window sets closable = false.
  3. Per-pane “open maximised” at creation time (first-class flag, not layout-blob surgery).
  4. Async per-pane close interceptor (e.g. onPaneCloseRequested(paneId, proceed)) so the host can show a dialog and then allow/cancel the close.
  5. Generic three-button choice dialog beside showConfirmDialog (used for Save / Discard / Keep editing).
  6. Initial appearance default (Dark) configurable if not already possible.
  7. Add Lunicle to publishAllToLibsRepo targets (../../lunicle/main/libs-repo, overridable property).

Compat check: build Lunamux against toolkit source (composite build) after each change; no lunamux code edits expected since everything is additive.

Phase 2 — Lunicle: dependency plumbing

  1. Copy Lunamux's settings.gradle.kts pattern: libs-repo Maven repo + sibling auto-detect composite build + useArtifacts escape hatch.
  2. Version-catalog entries for toolkit-core/toolkit-web; web module depends on them.
  3. First toolkit publish into lunicle/main/libs-repo (version bump per the /bump-toolkit workflow).

Phase 3 — Lunicle: view-model extensions (client module)

The one structural change: window management replaces the single-dialog model.

  1. MainScreenBackingViewModel's ActiveDialog (one dialog at a time) gives way to a window registry: multiple open issues, each with its own IssueBackingViewModel instance/scope; focus-existing on reopen. Registry lives shell-side (bootstrap), VM keeps deep-link resolution and board state.
  2. Expose dirty-state from IssueBackingViewModel for existing-issue edit mode, plus explicit save-then-close and discard paths (new-issue discard = delete draft row, as Cancel does today).
  3. Board refresh trigger: on successful issue save/delete, notify the board VM to reload (same pattern as the existing session-change and project-settings-written reloads). Also covers new-project → project-list refresh.

Phase 4 — Lunicle: new web shell (replace the web UI)

  1. New bootstrap: mountAppShell(AppShellSpec) — no worldSource, no appSettingsContent, sidebar+tabstrip off, InMemoryPersister, Lunamux Dark default, + menu = New issue (+ New project when permitted), sign-in/profile as trailing custom action.
  2. Board window: non-closable, opens maximised; content = board renderer rebuilt on darkness styles (columns, cards, drag/drop) driven by MainScreenBackingViewModel; project switcher inside the window (without “New project…”).
  3. Issue windows: read view (rendered markdown) + Edit toggle; close goes through the interceptor → Save/Discard/Keep dialog when dirty. New issue opens in edit mode.
  4. New-project modal on the toolkit dialog pattern, driven by EditProjectBackingViewModel (today's fields).
  5. Port sign-in flows (Google GIS / GitHub popups), comment/resolution/profile dialogs, markdown editor mounting, lightbox — restyled to dt- idioms.
  6. Deep links: keep ?project=/?issue= parsing and replaceState sync; a deep-linked issue opens its window after the board mounts. URL reflects the most recently focused issue window.
  7. Retire the old views/styles.css once parity is reached.

Phase 5 — Verify & release

  1. Feature pass on Lunicle: signed-out browsing, sign-in, board CRUD + drag/drop, multi-issue windows, unsaved-changes flows, deep links, permissions gating, board auto-refresh on save.
  2. Lunamux regression: build + run against the new toolkit; I flag every risk area (DOM-class coupling list above); you do manual testing.
  3. Bump toolkit version, publishAllToLibsRepo (lunamux, notegrow, lunicle), prune old versions, pin in both consumers.

Risks & watch items

  • Lunamux DOM coupling: any accidental change to .dt-* class names/structure breaks lunamux silently. Mitigation: additive-only flags; default rendering path untouched; targeted grep of lunamux's coupled selectors after each toolkit change.
  • + menu local-mode entanglement: suppressing “New tab” while keeping one implicit local-mode tab touches the same code path lunamux uses in source mode — needs care and a lunamux smoke check.
  • Multi-instance IssueBackingViewModel: written for one-dialog-at-a-time; verify no hidden shared state (e.g. in StorageRepository) before allowing N instances.
  • Draft contract vs. Save/Discard: new-issue drafts already exist server-side; “Keep editing” must not leak orphan drafts, and browser/tab close (no interceptor possible) keeps today's draft-cleanup semantics.
  • Iframe embedding (lunamux.dev embeds lunicle): preserve the no-hash, replaceState-only URL behaviour.
