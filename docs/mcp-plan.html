Lunamux / Lunicle

MCP support — and the OAuth server underneath it

The goal is one sentence: an agent — Claude Code, Claude Cowork, Cursor, anything — connects to Lunicle and can do exactly what the signed-in user can do, no more, acting on their behalf. Everything in this document exists because that sentence requires a real OAuth flow, and a real OAuth flow requires Lunicle to become something it currently is not. The good news is that Framnaflow already built this, in Kotlin, on Ktor, and it is running in production. This is a port, not a design.

Read first The one realization this all hangs on

If you take nothing else from this document, take this.

Lunicle is currently an OAuth client. It must become an OAuth server. Today, Google and GitHub are the authorization servers and AuthRoutes.kt consumes their authorization codes. That is the client role. MCP needs the opposite: Lunicle becomes an OAuth 2.1 resource server at /mcp, and something must be its authorization server — minting tokens whose audience is Lunicle itself.

This is not a technicality that can be worked around. The MCP specification says a client MUST NOT send a token to a server that the server's own authorization server did not issue, and a server MUST validate that a token was issued for it specifically. So none of the following can work, and none of them should be attempted:

  • Handing the agent a Google or GitHub access token. Wrong audience; the spec forbids accepting it.
  • Handing the agent the lunicle_session cookie value. Not a bearer token, no expiry check on read, no scope, no revocation story, and no client identity — you would never know which agent was acting.
  • A pasted personal access token as the primary path. See §4 — Framnaflow built exactly this, shipped it, and then turned it off.

The half you already own

An authorization server's hard problem is "who is this human?" — and Lunicle answers it today. users.upsert(identity) → sessions.create(user.id) is working federated identity, in production, over two providers. The new code is the token half, not the login half. That is why this is roughly 700 lines and not a quarter.

The principle that makes the whole thing safe

An access token resolves to a UserRecord — the same type a session cookie resolves to. That gives ApplicationCall.caller() a second implementation and changes nothing else. Every route, every AccessControl rule, every filtered read applies to the agent unchanged, because the agent is just another caller. Read AccessControl.kt's preamble — "the client is a renderer of permissions, never a source of them" — and note that this design is what makes that sentence literally true for a second transport. Framnaflow states the same rule in auth/AccessControl.kt:6: "Transport-agnostic authorization, shared by the Ktor /api routes and the MCP server so the two can never drift apart."

§2 The flow, end to end

What actually happens when a user types claude mcp add.

  1.  Agent  →  POST /mcp  (no token)
  2.  Lunicle →  401 + WWW-Authenticate: Bearer resource_metadata="https://…/.well-known/oauth-protected-resource"
  3.  Agent  →  GET  /.well-known/oauth-protected-resource        → names the authorization server
  4.  Agent  →  GET  /.well-known/oauth-authorization-server      → names /oauth/authorize, /oauth/token, …
  5.  Agent  →  POST /oauth/register                              → client_id  (DCR, unauthenticated)
  6.  Agent  →  opens the user's BROWSER at /oauth/authorize?client_id=…&code_challenge=…&resource=…
  7.  Lunicle →  reads lunicle_session cookie
                 signed in?    → render consent page
                 signed out?   → existing Google/GitHub sign-in first, then consent
  8.  User   →  clicks Approve  →  POST /oauth/consent
  9.  Lunicle →  302 back to the agent's redirect_uri with ?code=lun_code_…
 10.  Agent  →  POST /oauth/token  (code + code_verifier + resource)
 11.  Lunicle →  { access_token: lun_at_…, refresh_token: lun_rt_…, expires_in: 3600 }
 12.  Agent  →  POST /mcp  with Authorization: Bearer lun_at_…    → works, as that user, forever after

Steps 3–5 and 10–12 are machine-to-machine and invisible. The user sees exactly one thing: a browser tab at step 6–8 asking "Claude Code wants to act as you on Lunicle." That is the entire UX of connecting, and it is why no secret is ever pasted.

§3 Decisions taken

These are settled. Each one has a rejected alternative, recorded so nobody relitigates it in three weeks.

Build the authorization server; don't buy one

WorkOS, Stytch, Auth0 and Descope all sell MCP-shaped OAuth. Rejected, because the identity half already works here, an external AS would still need a way to resolve its users back to our users rows, and — decisively — a working reference in this exact stack already exists. The honest counterweight: token endpoints punish cleverness. Do not be clever. Port.

Reuse the session cookie at /authorize; do not re-federate

This is the one place Lunicle must deliberately diverge from Framnaflow. Framnaflow's /oauth/authorize redirects straight to Google (OAuthServer.kt:172) because Google is its only provider. Lunicle has two, so it cannot blindly pick one — it would have to render a provider chooser and add a second federation callback, with a new redirect URI to register in Google's console.

Instead: read lunicle_session. If it resolves to a UserRecord, go straight to consent. If not, show the existing sign-in, then consent. Less code, better UX, no new provider configuration.

Why the cookie is actually readable here

/oauth/authorize is a top-level browser navigation, not a framed or cross-site fetch. In production the cookie is SameSite=None; Secure and rides along. Locally it is SameSite=Lax, and Lax sends on top-level GET navigation. Both work with no change to cookie policy. The CSP frame-ancestors header is irrelevant — it governs who may embed a page, and nobody is embedding this one.

One flat mcp scope. No granular scopes.

An earlier draft of this plan proposed lunicle:read / lunicle:write / lunicle:admin. Rejected — it is more than the requirement needs. Framnaflow is explicit (auth/AccessControl.kt:9): "there is no token-level scope mechanism", and its consent page says "It will have the same rights you do in the web app." That is the requirement, stated exactly. The token says who you are; AccessControl says what that means. One mechanism, not two that can disagree.

Admin operations are not exposed over MCP at all

Rather than an admin scope, follow Framnaflow's instinct: some tools simply do not exist. No delete_project, no create_project, no role granting, no impersonation. A capability that has no tool cannot be abused by a confused agent, and this is the cheapest possible form of that guarantee. Revisit only when someone actually asks.

Opaque, prefixed, hashed tokens — never JWTs

We have a database and one container. Opaque means revocation is a DELETE rather than a blocklist we would have to invent. Prefixes (lun_at_, lun_rt_, lun_code_) let validation reject a wrong-type token before touching storage. Hashed at rest because — unlike session ids, which live only in a browser jar — these will sit in config files on developer laptops.

No personal access tokens

Framnaflow built a self-service fmcp_… token, shipped it, and then disabled it: McpServer.kt:107 reads ACCEPT_MCP_ACCESS_TOKENS = false, with the whole repository kept intact behind the flag and the UI hidden. They retreated to OAuth-only. Take the result and skip the detour.

§4 The settings dialog — this is the part to build

Assume the settings dialog and its section scaffolding exist. This describes the MCP section inside it. This is the piece Framnaflow does not have, and where Lunicle should be better than its reference.

What Framnaflow's UI actually is

Nothing, for the user. The token UI is hidden and disabled. The only surface is admin-only — "Settings → Users → OAuth connections". There is no way for a user to see or revoke their own connections. The server-side support is already written and simply has no screen: OAuthTokenRepository.listGrants() and revokeForUser(email, clientId) (OAuthRepositories.kt:293 and :306). Lunicle should build the screen.

Section title: Connections, not "MCP"

The toggle is the least interesting thing in the section after the first day. What the user comes back for is the list of what is connected and the ability to cut it off. Name the section for that.

Three states

State A — off (the default). A single toggle, a one-line explanation, nothing else. The explanation must say what the feature is in plain words, because "MCP" means nothing to most people:

  [ ] Let AI agents act on your behalf
      Connect Claude Code, Claude Cowork, or another AI agent to Lunicle.
      It will be able to do exactly what you can — nothing more.

State B — on, nothing connected yet. Reveal the server URL and a ready-to-paste command. Both need a copy button; nobody types these correctly.

  [x] Let AI agents act on your behalf

      Server URL
      https://lunicle.lunamux.dev/mcp                          [copy]

      Claude Code
      claude mcp add --transport http lunicle \
        https://lunicle.lunamux.dev/mcp                        [copy]

      Then run /mcp in Claude Code and choose Authenticate.
      Other agents: add a custom connector with the server URL above.

State C — on, with connections. The list is the point of the screen.

  Connected agents

    Claude Code        connected 3 days ago · last used 2 min ago    [Revoke]
    Cursor             connected 1 Jul                · last used 4 Jul  [Revoke]

Behaviour notes for whoever builds it

  • The toggle defaults off and is a real kill switch: while off, /oauth/authorize refuses and /mcp rejects that user's tokens. Turning it off does not delete grants — turning it back on restores them. Deleting is what Revoke is for, and conflating the two would surprise people.
  • Turning it off while agents are connected needs a confirm. "2 connected agents will stop working. They'll work again if you turn this back on."
  • Revoke is immediate and irreversible. It kills the whole refresh family, so the agent cannot silently refresh its way back in. The agent must redo the browser flow.
  • Client names come from DCR and are therefore self-reported by the client. Anyone can register a client called "Claude Code". Escape the name on render — never trust it — and do not let it be the only thing the user sees. This is a real, if minor, spoofing surface.
  • The consent page is the actual security boundary, not the toggle. The toggle is an affordance and a comfort. Worth being honest about that in review.

The one thing the dialog must not do

Do not render a "connect" button that starts the OAuth flow from inside Lunicle. The flow is always initiated by the agent — the agent needs to be the OAuth client, hold the PKCE verifier, and receive the code at its own redirect URI. Lunicle's UI only ever displays the URL and lists the result. A "Connect to Claude Code" button cannot exist and would mean someone has misunderstood the direction of the protocol.

§5 Schema

Five new tables and one new column. Framnaflow's are Firestore documents; ours are SQLDelight, which is strictly better here — consume() and rotateRefresh() are read-then-delete races in Firestore, and transactions on a serialized dispatcher for us.

Migration mechanics — get this right or the build fails confusingly

Current schema version is 3 (databases/1.db, 2.db, 3.db are committed; 1.sqm and 2.sqm exist). So this work adds 3.sqm and generates databases/4.db. MigrationTest.kt is what verifies the two agree — SQLDelight's own verifyMigrations is deliberately off, and server/build.gradle.kts explains at length why. Run the test.

Plus one column on users, for the toggle:

  ALTER TABLE users ADD COLUMN mcp_enabled INTEGER NOT NULL DEFAULT 0;

Every ON DELETE CASCADE above is load-bearing and works only because Database.kt sets foreign_keys as a connection property and verifyPragmas() refuses to start otherwise. Deleting a user must not leave live tokens pointing at nobody. Read that file's preamble before assuming a cascade works.

Refresh families and reuse detection

Port this exactly (OAuthRepositories.kt:245). Every access+refresh pair shares a family_id. Rotating a refresh token marks the old one consumed and issues a new pair in the same family. If an already-consumed refresh token is ever presented again, the only explanation is theft — revoke the entire family and log it. It is about fifteen lines and it is the best security property in the design.

Housekeeping

Two mechanisms, and they are not the same one.

  • Expiry is checked on read. Non-negotiable, and this is where we depart from SessionStore. Sessions.kt candidly documents that lookup does not check expiry and that an old session stays usable until a restart — "the next thing to fix if sessions ever carry more than a user id." A token that outlives its advertised expires_in while sitting in a file on a laptop is that bug with teeth. Put expires_at > ? in the query.
  • Sweeping is startup housekeeping only. Follow the existing convention: add the code/token/login-state sweeps to the same launch{} in Application.module that already calls sessions.deleteExpired(). Framnaflow runs a 6-hourly reaper (Application.kt:392) because Cloud Run instances are long-lived; Railway replaces our container on every deploy, and — critically — because expiry is checked on read, a missed sweep is a disk-space question, never a security one.

Deriving the issuer

Framnaflow re-implements base-URL resolution in two files (OAuthServer.kt:31, McpServer.kt:110). Do not copy that. Lunicle already has ApplicationCall.serverOrigin() in AuthRoutes.kt, and it is better — it handles X-Forwarded-Proto and takes the authority verbatim from the Host header rather than recomposing scheme + host + port. Read its comment: recomposing yields https://lunicle.lunamux.dev:80 in production, and no local run can reproduce that. Promote serverOrigin() to internal and use it everywhere. The issuer in the metadata and the resource in the token must agree byte for byte, so there must be exactly one function that computes them.

§8 Traps

Two of these are bugs Framnaflow already paid for. One is a correction to an earlier draft of this plan. The rest are ordinary.

1 — GET /mcp must bypass ContentNegotiation, or every client fails to connect

Read McpServer.kt:128. The GET /mcp handler returns 405 via respondText — not respond(status, body) — deliberately. When an MCP client opens the optional SSE stream it sends Accept: text/event-stream. Negotiating a JSON body against that Accept produces 406, and clients treat 406 as a fatal connection error rather than "this optional stream isn't offered." A plain 405 tells the client to carry on.

Lunicle installs ContentNegotiation { json() } at Application.kt:139. It will hit this exactly. The symptom is "the server doesn't work in Cursor" with nothing useful in the log.

2 — Serve the well-known documents at every path clients probe

OAuthServer.kt:90–94 registers five discovery routes, not two. Different clients append /mcp to the well-known path, or ask for openid-configuration instead. Each alias is one line. Skipping them produces a client that silently cannot discover the AS, which looks identical to the server being down.

3 — Correction: the loopback-port problem is not real

An earlier draft warned that exact redirect_uri matching would break Claude Code because its callback port varies, and advised matching scheme/host/path while ignoring the port. That was wrong. Framnaflow exact-matches against the URIs the client registered via DCR (OAuthServer.kt:139) and it works, because the client registers its actual redirect URI before ever using it. isAllowedRedirectUri (OAuthServer.kt:49) only gates the shape at registration time: https, http://localhost, http://127.0.0.1, or a custom app scheme like cursor://. Do exact matching. Do not invent port-insensitive comparison — it would be a real weakening for no gain.

4 — Validate the client and redirect_uri BEFORE redirecting anywhere

OAuthServer.kt:137 makes the ordering explicit, and it matters: if client_id or redirect_uri is bad you must render a plain error page, not redirect. Redirecting an error to an unvalidated redirect_uri is an open redirector. Only once the URI is confirmed to be one this client registered may errors be sent there.

5 — POST /oauth/register is unauthenticated, on a half-gigabyte volume

That is by design — it is what lets Claude Code self-register. It also means anyone on the internet can write rows to oauth_clients. Rate-limit it, and sweep registrations that never completed an authorization. Framnaflow runs on Cloud Run and does not worry; Lunicle's volume has a trial ceiling and Sessions.kt's preamble already worries about exactly this class of unbounded growth.

6 — Things that fall out for free (notice them, don't rebuild them)

Role changes propagate instantly. Because every request re-derives permissions through AccessControl rather than baking them into the token, an admin removing someone's role immediately narrows their agent too. No token invalidation needed.

Revocation is instant because /mcp is stateless — every POST is authenticated independently, so there is no session to outlive a deleted row.

Re-check on refresh. One thing that does not fall out: mirror OAuthServer.kt:291 and re-verify at rotation that the user still exists and still has mcp_enabled. Otherwise a 30-day refresh token outlives the toggle.

§9 Stages

Four, each independently verifiable. Do not start the next until the previous one is observably working — this is a protocol, and protocols fail silently.

Stage 1 — the transport, with no OAuth at all

POST /mcp, the JSON-RPC dispatch (initialize, ping, tools/list, tools/call), the GET → 405 handler, and two read-only tools (list_projects, get_board). Authenticate with a hardcoded token read from a system property. This proves the transport and the tool layer before any OAuth exists to confuse the diagnosis.

Exit

claude mcp add --transport http lunicle http://localhost:8080/mcp with the token in a header, and /mcp in Claude Code lists two tools and calls them.

Stage 2 — the authorization server

Schema (3.sqm + 4.db), the four stores, discovery documents, DCR, /authorize with cookie reuse, the consent page, /token with PKCE, refresh rotation with family reuse detection, and revocation. Delete the hardcoded token from Stage 1.

Exit

Add the server by URL only, with no secret anywhere. /mcp → Authenticate → a browser opens → consent → tools work. Then: restart the server and confirm the agent is still connected (persistence), and delete the token row and confirm the next call 401s (statelessness).

Stage 3 — the Connections section

The mcp_enabled column, the three /api/mcp routes, the wire types, and the settings section described in §4. This is where the other agent's dialog work lands.

Exit

Connect an agent, see it appear in the list by name, revoke it, watch the very next tool call 401. Toggle off with a live connection and confirm the confirm dialog, then that the agent stops, then that toggling back on restores it without re-consent.

Stage 4 — write tools

create_issue, update_issue, move_issue, add_comment, and the instructions block. Then docs/mcp-setup.html for users, modelled on Framnaflow's docs/mcp-server-setup.md.

Exit

The real test, and it must be run deliberately: sign in as a non-admin with no roles, connect an agent, and confirm every write tool returns a clean permission error rather than working. Then grant create_issue and confirm exactly that one starts working. If an agent can do something its user cannot, the entire premise of this document has failed, and it will have failed quietly.
