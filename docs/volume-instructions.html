Stage 2 — the database volume

The steps that need your Railway account: one volume, one mount path, and a look at two lines of log. Everything else — creating the schema, migrating it, making the mount writable — the server and its entrypoint already do. This is the shortest document in the set, and the one place where getting it wrong is invisible until it costs you every account you have.

Read first Why this needs a volume at all

One paragraph of context, then one trap that is already handled.

A container's filesystem is thrown away. Railway replaces the whole container on every deploy — that is what makes deploys safe and repeatable, and it is also why Stage 1's counter reset to zero each time. SQLite is one file. Put that file inside the container and it dies with the container; put it on a volume — a disk that is mounted into the container at start and outlives it — and it doesn't. That is the entire mechanism. There is no clever part.

The failure mode is silence. A server whose database is in the wrong place works perfectly. It signs people in, it counts, it looks healthy for as long as you care to test it. It loses everything on the next unrelated redeploy, with nothing in the logs to explain why. That is the only reason this document exists, and it is why Step 3 is not optional.

The trap you don't have to fall into

A Railway volume mounts owned by root, and Lunicle's container runs as an unprivileged user (issues, uid 10001) — so the server cannot write to its own database. SQLite reports this as unable to open database file, which points at nothing. Railway's documented fix is to set RAILWAY_RUN_UID=0 and run everything as root. Do not do that, and you don't need to. scripts/container-entrypoint.sh already handles it: it starts as root, chowns the mount, and drops to issues before starting the JVM. Root exists for exactly one chown. Setting RAILWAY_RUN_UID would undo this, not help it.

Step 1 Create the volume and attach it

Dashboard or CLI. Both do the same thing; pick either.

In the dashboard

  1. Open the Lunicle project.
  2. Press ⌘K for the command palette and choose to create a volume — or right-click the project canvas and do the same there.
  3. Pick the Lunicle service when it asks what to connect the volume to.
  4. Set the mount path to /data — exactly this, see below.

Or with the CLI

# From the repo, against the linked project.
$ railway link
$ railway volume add -m /data -s <your-lunicle-service>

# Confirm it exists and is mounted where you think.
$ railway volume list

Why /data, and why exactly that

Two reasons. It must not be /app — that is where Railway puts your application, and a volume is not an overlay, so mounting there would hide the server. And /data is what everything else in this repo already assumes: it is the VOLUME declared in the Dockerfile, the directory the entrypoint chowns, and the path scripts/container-up.sh mounts locally. Choosing a different path works — the server reads the mount path from Railway rather than hardcoding it — but you would be the only one who knows.

Step 2 Set no variables at all

This step is deliberately empty. Read it anyway — it's the part people undo.

Railway injects RAILWAY_VOLUME_MOUNT_PATH into the container automatically whenever a volume is attached, and that is exactly what the server resolves its database path from. So a correctly-attached volume needs no database variable. Attach it and deploy.

The escape hatch exists if you need it: LUNICLE_DB_PATH overrides the path outright. It is there for a non-Railway host. If you set it on Railway you are opting out of the mechanism that already works, and if you point it somewhere that isn't the volume you get the silent data loss this whole document is about.

RAILWAY_VOLUME_MOUNT_PATHRailway, automaticallyLeave alone

Step 3 Read the log. This is the actual verification.

Two lines. Everything in this document is aimed at making them say the right thing.

Deploy, then open the service's Deploy Logs. The server says where its database is, on every boot, on purpose — so that this is a five-second check rather than an investigation.

What a correct deploy says

INFO  Database - Database: /data/lunicle.db (via RAILWAY_VOLUME_MOUNT_PATH)
INFO  Database - Database: fresh — creating schema at version 1

via RAILWAY_VOLUME_MOUNT_PATH is the phrase that matters: it means the path came from a real attached volume rather than a guess. On the first deploy you'll see fresh — creating schema. On every deploy after that:

INFO  Database - Database: schema is current at version 1

Which is the good news you want — it means it found the database that was already there.

What a broken deploy says

WARN  Database - Database: /data/lunicle.db — NO PERSISTENT VOLUME.
      Data will be lost on redeploy. Attach a Railway volume, or set
      LUNICLE_DB_PATH. See docs/volume-instructions.html.

If you see that WARN, stop

The server is running and the app works — and every account it creates from now on will be destroyed by the next deploy. It means no volume is attached to this service (so Railway injected no mount path). Go back to Step 1. Do not "test it later": the longer it runs, the more real accounts are on the disk that is about to disappear.

Step 4 Prove it — the stage's exit criterion

Sign in, increment, redeploy, sign back in, count still there.

This is the whole of Stage 2, and it is one test. Do it through the iframe on lunamux.dev, not against lunicle.lunamux.dev directly — the same rule as the OAuth document, and for the same reason: the framed context is the one that breaks, so the unframed test passes and proves nothing.

  1. Open https://lunamux.dev/?issues=1#/issues.
  2. Sign in with Google or GitHub. The popup opens; you come back with your name on screen.
  3. Increment the counter a few times. Note the number.
  4. Redeploy the service from the Railway dashboard, and wait for it to go green.
  5. Reload the page.

Pass

You are still signed in — sessions live on the volume too now, so a redeploy no longer signs anyone out — and the counter shows the number you left it at. If you sign out and back in, it is still yours: the count is keyed to your provider identity, not to your cookie.

Fail

Counter back to — or zero, or you're signed out. Go read the two log lines in Step 3; they will tell you which of the two things went wrong.

Step 5 Things that will surprise you later

None of these need action today. All of them cost an afternoon if met cold.

Redeploys now have downtime

Railway refuses to run two containers against one volume — deliberately, to stop exactly the kind of corruption two SQLite writers would cause. So a service with a volume gets a small gap on every redeploy, even with a healthcheck configured. This is a good trade and not a misconfiguration: it is also what lets the server assume it is the only writer.

Replicas are off the table

One volume per service, and no replicas on a service that has one. Scaling horizontally means leaving SQLite, which is a Stage-later problem and named as such in stages.txt.

Consider a draining period

Railway's default RAILWAY_DEPLOYMENT_DRAINING_SECONDS is 0 — an immediate SIGKILL. The server closes its database on shutdown so SQLite can checkpoint its write-ahead log back into the main file; a hard kill skips that. SQLite recovers on the next open regardless, so this is tidiness rather than safety, but setting it to 30 costs nothing.

Size, and the trial ceiling

Free/Trial volumes are 0.5 GB; Hobby 5 GB; Pro 50 GB. A users table, a sessions table and one integer each will not trouble half a gigabyte for years. Worth knowing rather than worth doing anything about.

Backups are not solved

Railway offers volume backups, and a snapshot of a live SQLite file is not guaranteed to be consistent — the .db and its -wal must be captured together. Litestream is the real answer and it is deliberately deferred (see stages.txt). Until then, the honest position is: this data is a POC's data, and it is not backed up.

Reading the volume when you need to

# Browse it interactively.
$ railway volume browse /

# Or pull the database down and open it locally.
$ railway volume files download /data/lunicle.db ./lunicle.db
$ sqlite3 lunicle.db "SELECT id, provider, display_name FROM users;"

Deleting the volume is soft, briefly

A deleted volume is queued rather than destroyed, and is recoverable for about 48 hours via an emailed link. Do not rely on this; do notice that it exists if you delete the wrong thing.

Local The same thing, on your machine

You do not need a deploy to test any of this, and you shouldn't.

scripts/container-up.sh runs the same image with a real Docker volume and passes RAILWAY_VOLUME_MOUNT_PATH=/data, so the local container resolves its database by the identical mechanism the deploy does. A named Docker volume, specifically: those come up root-owned exactly as Railway's do, so this genuinely exercises the entrypoint's chown-and-drop. A bind mount would inherit your home directory's ownership, work by accident, and prove nothing.

$ ./scripts/container-up.sh
# … sign in, increment, then:
$ ./scripts/container-down.sh      # keeps the volume
$ ./scripts/container-up.sh --no-build
# → still signed in, count intact. That is the exit criterion, locally.

$ ./scripts/container-down.sh --wipe   # deletes the volume
# → next start logs "fresh — creating schema at version 1"

--wipe is worth knowing about: creating the schema on an empty volume is a code path production runs exactly once, on the very first deploy, where it is most expensive and least observable to get wrong. This runs it as often as you like.

A plain ./gradlew :server:run keeps its database under server/build/lunicle.db, so ./gradlew clean throws it away.

Later Changing the schema, once there's data

Not needed now. Needed the first time you touch a .sq file.

From the moment the volume has real accounts on it, a schema edit is a migration rather than a rewrite. The build enforces this — verifyMigrations is on, so changing a .sq without a matching migration fails the build rather than discovering itself in production.

  1. Edit the .sq file.
  2. Add server/src/main/sqldelight/migrations/<n>.sqm — the SQL that gets a version-n database to version n+1.
  3. Run ./gradlew :server:generateMainLunicleDatabaseSchema to snapshot the new version, and commit the .db it writes under server/src/main/sqldelight/databases/.

The server applies migrations itself at startup, tracked in SQLite's own user_version — you will see migrating schema 1 → 2 in the deploy log. It runs at startup because it has to: the volume is not mounted during the build, nor during pre-deploy, so container start is the first moment the file exists at all.

Rolling back is not free

A database migrated to version 2 will refuse to start under a build that expects version 1, with a log line saying so. That is deliberate: the old build's queries do not match the volume, and letting it write anyway is the unrecoverable version of this problem. Roll forward.
