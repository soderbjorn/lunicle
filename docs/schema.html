1 Layering — two sides, two kinds of repository

CLARIFICATIONS #2: the server has repositories too, and they are not the client's.

╔═ :client (KMP — browser today, iOS later) ═══════════════════╗
  View  (DOM; renders State, forwards intent, no logic)
    │
  BackingViewModel  (one immutable State over one StateFlow)
    │
  StorageRepository  (too business-y for the view model; fans out
    │                 across several APIs / sources; caches)
    │
  LunicleApi  (typed HTTP, nothing else)
╚══════════════════════════════════════════════════════════════╝
                           │  HTTP
╔═ :server (JVM) ══════════════════════════════════════════════╗
  Routes  (parse, AUTHORIZE, respond — see §2)
    │
  *Repository  (server-side: multi-store transactions, filesystem
    │           + database together, the rules)
    │
  *Store  ("DatabaseService": SQL and nothing else)
    │
  SQLDelight → SQLite on the volume
╚══════════════════════════════════════════════════════════════╝

The two StorageRepositorys share a name and nothing else

Worth being blunt about, because the name collides and the collision is the whole point of the clarification. The client's repository sits above HTTP and cannot see a database — it exists so a view model never mentions transport, and so that logic which spans several calls (load the project list and the session before MainScreen can render) has somewhere to live that isn't the view model. The server's repositories sit below HTTP and above SQL — they exist so a route never mentions a transaction, and so that logic spanning several stores has somewhere to live that isn't the route handler.

Same motivation, opposite side of the wire, no shared code. mvp.txt's "StorageRepository → DatabaseService" is the client half and the server half of one chain, not one object.

The server-side repositories the MVP actually needs

Not speculative — each one exists because there is a specific piece of logic that belongs in neither the route nor a store:

RepositoryThe logic it owns
ProjectRepository Create = insert the project and seed its labels, components and statuses, in one transaction (§13). Rename = trim, upper-case the prefix, Unicode-fold the uniqueness check (§6). None of that is SQL, and none of it is HTTP.
IssueRepository Publish = write the issue, its labels and its components together or not at all. Delete = rows cascade, then the attachment files have to go too — database and filesystem in one operation, which is exactly "wires up multiple data sources".
AttachmentRepository The volume and the table, kept in step: write file → insert row, unlink on delete, sweep orphans at startup (§10).
AccessControl Every permission question, in one place. See §2 — this one is load-bearing.

The *Store classes stay exactly what UserStore and SessionStore already are: one class per table, SQL in, data class out, no decisions. That is the "DatabaseService" mvp.txt asks for, and it already exists in this shape — which is why the naming here follows the code rather than the memo.

2 Security — the server decides, always

CLARIFICATIONS #2, first line. The most important paragraph in this document.

The client is a renderer of permissions, never a source of them

Everything the browser knows about what it may do — isAdmin on the wire, a greyed-out delete button, a card that will not drag — is an affordance: it exists so a user is not invited to do something that will fail. None of it is enforcement. The bundle is JavaScript on someone else's machine; every flag in it is editable, every disabled button is re-enablable from the console, and every request it declines to send can be sent by hand with curl. A permission that lives in the client is not a permission.

So every mutating route re-derives the answer server-side, from the session, before it touches a store — not from anything the request body claims. A client that lies to itself gets a 403; it does not get a deleted project.

One place, one function

The rules are small enough to fit in one class, and that is precisely why they should not be scattered across route handlers — a check that exists in six places is a check that is missing from the seventh.

// AccessControl — the ONLY thing that answers a permission question.
// Takes the caller from the session, never from the request body.

fun canEditIssue(user: UserRecord?, issue: IssueRecord): Boolean =
    user != null && (
        user.isAdmin ||
        issue.createdBy == user.id ||
        hasRole(user, issue.projectId, "change_unowned_issues")
    )

fun canCreateIssue(user, projectId) = user?.isAdmin == true || hasRole(user, projectId, "create_issue")
fun canComment(user, projectId)    = user?.isAdmin == true || hasRole(user, projectId, "comment_on_issue")

// Projects are admin-only to mutate; see §14 D7.
fun canEditProject(user)  = user?.isAdmin == true
fun canDeleteProject(user) = user?.isAdmin == true

// Reading. The public flag is a READ gate, and it is the one rule that
// says yes to a caller with no session at all.
fun canReadProject(user, project) = project.isPublic || user != null

Drag-and-drop is not a special case, and must not become one

Moving a card between columns is a status_id write on an issue, so it goes through canEditIssue — the same function the editor uses. Worth stating because a board invites a shortcut: a "just move it" endpoint that skips the check because dragging feels lighter than editing. It is not lighter. It is the same write, and an unchecked one would let anyone drag anything to Closed.

Filtering reads, not just refusing writes

The other half of "the server enforces" is that it must not send what the caller may not see. Refusing a write is the obvious half; quietly shipping a private project's name to a signed-out visitor and trusting the bundle to hide it is the half that gets forgotten. So:

  • Signed out → the project list contains public projects only. Not "all projects, hidden in the UI".
  • Signed out → issues, comments and attachments are readable only under a public project.
  • ?project= naming a private project, signed out → resolves to no project, exactly as if the name did not exist. Answering "that project is private" would confirm it exists, which is the thing being withheld.
  • email never crosses the wire at all (§4).

Attachments are behind the same gate as the issue they hang on

GET /api/attachments/<id> is a URL that appears inside rendered markdown, so it is trivially shareable and will end up pasted places. It resolves the owning issue and runs canReadProject before streaming a byte. The storage_key is random and never appears in a URL, so guessing one buys nothing either — but the route checking is what makes that a second line of defence rather than the only one.

4 users

Two names now, and they mean different things.

CREATE TABLE users (
    id INTEGER PRIMARY KEY AUTOINCREMENT,

    provider TEXT NOT NULL,             -- AuthProvider.name: GOOGLE | GITHUB
    provider_id TEXT NOT NULL,          -- Google's `sub`, GitHub's numeric `id`

    -- The name the provider gave us, refreshed on every sign-in. Per
    -- bullet 7 this is what the sidebar shows: the GitHub *username*, or
    -- the Google *name*. NOT NULL because the server always resolves
    -- something (see the box below) — a blank name reads as a bug.
    provider_name TEXT NOT NULL,

    -- The user's own override, and nothing else. Null means "no override"
    -- rather than "no name", which is why it is nullable rather than
    -- defaulted to the provider's — copying the account name in here once
    -- would freeze it, and a later rename upstream would never follow.
    display_name TEXT,

    -- Nullable, and that is a fact: GitHub's /user returns null for a
    -- private address. NULL means "we do not know" — different from "" and
    -- different from "they have none". Never an identity key; see below.
    email TEXT,

    is_admin INTEGER NOT NULL DEFAULT 0,
    created_at INTEGER NOT NULL,

    UNIQUE (provider, provider_id)
);

How provider_name is resolved, and why it can't be null

Bullet 7 wants "Signed in via GitHub as <github-username>" but "…via Google as <Google-name>" — two different fields. So the server resolves per provider, reusing the fallback chain OAuthProviders.kt already has: GitHub → login, which is always present. Google → name, else the email's local part, else "Google user". Every branch terminates, so the column is NOT NULL and no reader ever has to handle a nameless user.

What the UI shows is then display_name ?: provider_name — total, one line, and the override stays purely additive.

Email is not a key, and must never become one

The existing Users.sq argues this and it survives intact: an email is mutable and recyclable, so matching on it would either fork an account on rename or hand one person another's row when a provider frees an old address. UNIQUE (provider, provider_id) stays the only identity. email carries no constraint on purpose — the same human signing in via both Google and GitHub is two accounts by design, and they will share an address.

First user becomes admin — in one statement

upsert:
INSERT INTO users (provider, provider_id, provider_name, email, is_admin, created_at)
VALUES (
    ?, ?, ?, ?,
    -- Evaluated before this row lands, so it is 1 only on a genuinely
    -- empty table. EXISTS rather than count(*) — it stops at the first row.
    (SELECT CASE WHEN EXISTS(SELECT 1 FROM users) THEN 0 ELSE 1 END),
    ?
)
ON CONFLICT (provider, provider_id) DO UPDATE SET
    provider_name = excluded.provider_name,
    -- COALESCE, not assignment: GitHub stops returning an email the moment
    -- a user flips it private, and a later sign-in must not erase what an
    -- earlier one learned. Absent means "no news", not "gone".
    email = COALESCE(excluded.email, users.email)
    -- is_admin and display_name are deliberately absent. Recomputing admin
    -- on every sign-in would be a bug with teeth, and display_name is the
    -- user's — the provider has no business overwriting it.
RETURNING id, provider, provider_id, provider_name, display_name, email, is_admin;

The naive reading of "first user signed in becomes the admin" is SELECT count(*) then insert, which races: two people signing in at once on a fresh database both see zero and both become admin. Doing it inside the INSERT closes it. DatabaseDispatcher already serializes every query to one thread so this cannot bite today — this is belt to that brace, and it costs one subquery on a statement that runs once per sign-in.

5 roles & project_roles

A fixed vocabulary, granted per project. Read only by §2.

-- Hardcoded and not user-editable. Rows are seeded at database creation
-- and there is no route that writes here.
CREATE TABLE roles (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    -- `key` is a keyword in enough dialects to be worth dodging.
    role_key TEXT NOT NULL UNIQUE,
    description TEXT NOT NULL
);

-- A user may hold many roles in a project, hence the composite key rather
-- than a role column on some membership row.
CREATE TABLE project_roles (
    user_id INTEGER NOT NULL,
    project_id INTEGER NOT NULL,
    role_id INTEGER NOT NULL,
    PRIMARY KEY (user_id, project_id, role_id),
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE,
    FOREIGN KEY (project_id) REFERENCES projects(id) ON DELETE CASCADE,
    FOREIGN KEY (role_id) REFERENCES roles(id) ON DELETE CASCADE
);

The seeded rows, from the clarification:

role_keyGrants
create_issueCreate issues in this project.
comment_on_issuePost comments on this project's issues.
change_unowned_issuesEdit issues they did not create.

Admin is a column, not a role — and that is deliberate

"The admin role can do everything" could be a fourth row here, but it should not be. Admin is global — bullet 5 makes the first user to sign in the admin of the whole instance, before any project exists to grant a role in. A row in project_roles is by definition per-project, so it cannot express that. users.is_admin can, and every check in §2 reads user.isAdmin || hasRole(…) — one branch, server-side.

6 projects

Name, prefix, public flag. No blob.

CREATE TABLE projects (
    id INTEGER PRIMARY KEY AUTOINCREMENT,

    -- COLLATE NOCASE on the column makes both the UNIQUE index and every
    -- `=` against it case-insensitive. Trimmed server-side first —
    -- "Lunamux " and "Lunamux" are the same project to a human, and
    -- trailing space is invisible in the UI that would show the clash.
    name TEXT NOT NULL COLLATE NOCASE UNIQUE,

    -- The "FOO" in FOO-123. Unique across all projects, not just non-null:
    -- if two projects shared a prefix, FOO-123 would name two different
    -- issues and every ticket reference in every commit message would be
    -- ambiguous. Upper-cased server-side by convention.
    name_prefix TEXT NOT NULL COLLATE NOCASE UNIQUE,

    is_public INTEGER NOT NULL DEFAULT 0,
    created_at INTEGER NOT NULL,

    -- So the join tables can point at the (id, project_id) pair. See §8.
    UNIQUE (id)
);

The casing guarantee is ~95% structural, and the rest is a check — accepted, D1

COLLATE NOCASE folds ASCII A–Z only, so Ärenden/ärenden would both get in on the constraint alone. So ProjectRepository also runs a Unicode-aware lowercase() comparison before insert and rename, which catches åäö in practice. It is a check rather than a constraint, so it races in theory — and does not in fact, because DatabaseDispatcher pins every query to one thread. If that ever changes, this is on the list of things that quietly stop being true.

7 labels, components, statuses

Three identical shapes. Per project, duplicated across projects by design.

CREATE TABLE labels (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    project_id INTEGER NOT NULL,
    name TEXT NOT NULL COLLATE NOCASE,
    FOREIGN KEY (project_id) REFERENCES projects(id) ON DELETE CASCADE,
    -- Unique *within* a project. "It can have duplicates (for different
    -- projects)" is exactly this constraint and no other.
    UNIQUE (project_id, name),
    -- Not redundant with the PK: it is the target the composite FK in
    -- issue_labels needs. SQLite requires a UNIQUE index on precisely the
    -- referenced column pair. See §8.
    UNIQUE (id, project_id)
);

CREATE TABLE components (   -- identical shape
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    project_id INTEGER NOT NULL,
    name TEXT NOT NULL COLLATE NOCASE,
    FOREIGN KEY (project_id) REFERENCES projects(id) ON DELETE CASCADE,
    UNIQUE (project_id, name),
    UNIQUE (id, project_id)
);

CREATE TABLE statuses (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    project_id INTEGER NOT NULL,
    name TEXT NOT NULL COLLATE NOCASE,
    -- The board is "each column represents a status", so the columns need
    -- an order. Without this they'd come back in rowid order, which is
    -- insertion order, which is right by luck until someone adds one.
    position INTEGER NOT NULL,
    FOREIGN KEY (project_id) REFERENCES projects(id) ON DELETE CASCADE,
    UNIQUE (project_id, name),
    UNIQUE (id, project_id)
);

The seeds, verbatim from the clarification:

labelsBug, Feature, Improvement, Codebase
componentsDesktop, Server, Android, iOS
statusesNew, Backlog, Ready for development, In progress, Closed (position 0–4)

8 issues — per project

CLARIFICATIONS #2 confirms it; the composite FKs make it structural rather than conventional.

CREATE TABLE issues (
    id INTEGER PRIMARY KEY AUTOINCREMENT,

    -- Per project, and not merely by convention: every label, component
    -- and status this issue can reach is constrained against THIS column
    -- via the composite FKs below. An issue cannot leak into another
    -- project's vocabulary because the database will not store the row.
    project_id INTEGER NOT NULL,

    -- The per-project number: the 123 in FOO-123. Distinct from the id,
    -- which is global and an implementation detail.
    number INTEGER NOT NULL,

    -- The clarification calls this the issue's "label", meaning its short
    -- description. Named `title` here because `labels` is already a table
    -- and `issue.label` vs `issue.labels` differing by one character while
    -- meaning entirely unrelated things is a bug generator. See D3.
    title TEXT NOT NULL,

    -- Markdown, produced by the WYSIWYG editor. See §11.
    description TEXT NOT NULL DEFAULT '',

    status_id INTEGER NOT NULL,

    -- Hidden until the editor's OK. "New issue" inserts the row straight
    -- away so that an inline image upload has an issue to attach to —
    -- but an unfinished issue must not appear on anyone's board. Cancel
    -- deletes the row outright; this flag covers the crash/closed-tab
    -- case, where the draft simply stays invisible.
    is_draft INTEGER NOT NULL DEFAULT 1,

    created_at INTEGER NOT NULL,
    -- Nullable + SET NULL: deleting a user must not delete their issues.
    -- The issue outlives the account; the board would otherwise lose
    -- history every time someone left. Note §2 reads this for ownership,
    -- so a null author is an issue only an admin or a
    -- change_unowned_issues holder can edit — which is correct.
    created_by INTEGER,

    -- The author when there is no account to point at: history imported
    -- from another tracker, written by somebody who has never signed in
    -- here. The name itself, because naming somebody does not create an
    -- account and minting one to hang this on would put a row in users
    -- that cannot sign in. Exclusive with created_by — see the CHECK.
    -- An imported issue is therefore unowned, landing on the same rule as
    -- a deleted author above: admin, or change_unowned_issues.
    created_by_external TEXT,

    FOREIGN KEY (project_id) REFERENCES projects(id) ON DELETE CASCADE,
    FOREIGN KEY (created_by) REFERENCES users(id) ON DELETE SET NULL,
    -- Composite: a status must belong to THIS issue's project. No ON
    -- DELETE — a status still holding issues must not be deletable, and
    -- SQLite's default RESTRICT is exactly right.
    FOREIGN KEY (status_id, project_id) REFERENCES statuses(id, project_id),

    UNIQUE (project_id, number),
    UNIQUE (id, project_id),

    -- One author or the other, never both. Both null is still "nobody",
    -- which is what ON DELETE SET NULL leaves behind. Without this, an
    -- imported name could sit alongside a real account and mask it on
    -- every read.
    CHECK (created_by IS NULL OR created_by_external IS NULL)
);

The trickery: cross-project assignment made unrepresentable

The clarification asks how to express "one issue can have many labels, out of the labels available to the project", and guesses it needs trickery. It does, and SQLite has it built in. A plain label_id foreign key would happily let a Project A issue carry a Project B label — the constraint you actually want spans two tables. Carrying project_id redundantly on the join and pointing composite foreign keys at both parents makes the mismatch impossible to write down:

CREATE TABLE issue_labels (
    issue_id INTEGER NOT NULL,
    label_id INTEGER NOT NULL,
    -- Redundant on purpose. It is what ties the two FKs to one project:
    -- both must agree on this single column, so a label from another
    -- project cannot satisfy them at the same time.
    project_id INTEGER NOT NULL,
    PRIMARY KEY (issue_id, label_id),
    FOREIGN KEY (issue_id, project_id) REFERENCES issues(id, project_id) ON DELETE CASCADE,
    FOREIGN KEY (label_id, project_id) REFERENCES labels(id, project_id) ON DELETE CASCADE
);

CREATE TABLE issue_components (  -- identical shape
    issue_id INTEGER NOT NULL,
    component_id INTEGER NOT NULL,
    project_id INTEGER NOT NULL,
    PRIMARY KEY (issue_id, component_id),
    FOREIGN KEY (issue_id, project_id) REFERENCES issues(id, project_id) ON DELETE CASCADE,
    FOREIGN KEY (component_id, project_id) REFERENCES components(id, project_id) ON DELETE CASCADE
);

The alternative — validating it in Kotlin on every write — is a check you can forget to make on the seventh route. This one cannot be forgotten, because the database refuses the row. All of it rests on PRAGMA foreign_keys = ON, which Database.kt already sets and already documents as the line that makes every FK in the schema mean anything.

Allocating the number

insert:
INSERT INTO issues (project_id, number, title, description, status_id, is_draft, created_at, created_by)
VALUES (
    ?,
    -- MAX+1, not COUNT+1: numbers are never reused after a delete.
    -- COUNT would hand FOO-12 to a second issue the moment the first was
    -- deleted, and every link and commit message naming FOO-12 would
    -- silently point at the wrong thing. UNIQUE(project_id, number) is
    -- the backstop if this is ever wrong.
    (SELECT COALESCE(MAX(number), 0) + 1 FROM issues WHERE project_id = ?),
    ?, ?, ?, 1, ?, ?
)
RETURNING id, number;

A consequence worth naming: opening "New issue" and cancelling burns a number, so the board can go FOO-12, FOO-14. That is the correct trade — gaps are cosmetic, reused numbers are corruption.

9 comments

Posted from a modal like the issue editor's.

CREATE TABLE comments (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    issue_id INTEGER NOT NULL,
    body TEXT NOT NULL,          -- markdown, same editor as the issue
    created_at INTEGER NOT NULL,
    created_by INTEGER,          -- SET NULL, same reasoning as issues
    created_by_external TEXT,    -- no account; exclusive with created_by, as issues
    is_draft INTEGER NOT NULL DEFAULT 1,
    FOREIGN KEY (issue_id) REFERENCES issues(id) ON DELETE CASCADE,
    FOREIGN KEY (created_by) REFERENCES users(id) ON DELETE SET NULL,
    CHECK (created_by IS NULL OR created_by_external IS NULL)
);

is_draft for the same reason as issues: the comment modal supports inline image upload, so the row must exist before the image does. Cancel deletes it; the flag covers the crash. No project_id — a comment reaches its project through its issue, and duplicating it here would be a second source of truth for a fact that already has one.

10 attachments

Metadata in SQLite, bytes on the volume. Accepted per D4.

CREATE TABLE attachments (
    id INTEGER PRIMARY KEY AUTOINCREMENT,

    -- Exactly one owner, enforced below. Two nullable columns rather than
    -- an (owner_type, owner_id) pair, because that pair cannot carry a
    -- foreign key at all — and losing FK cascade is how you end up with
    -- attachments pointing at deleted issues.
    issue_id INTEGER,
    comment_id INTEGER,

    filename TEXT NOT NULL,      -- as uploaded, for the download name
    mime_type TEXT NOT NULL,
    byte_size INTEGER NOT NULL,

    -- The file's name on the volume. Random, not derived from filename:
    -- a user-supplied name reaching the filesystem is a path-traversal
    -- bug waiting for "../../lunicle.db". This column is the ONLY thing
    -- that ever names a path, and nothing a user types reaches it.
    storage_key TEXT NOT NULL UNIQUE,

    created_at INTEGER NOT NULL,
    created_by INTEGER,
    created_by_external TEXT,    -- no account; exclusive with created_by, as issues

    FOREIGN KEY (issue_id) REFERENCES issues(id) ON DELETE CASCADE,
    FOREIGN KEY (comment_id) REFERENCES comments(id) ON DELETE CASCADE,
    FOREIGN KEY (created_by) REFERENCES users(id) ON DELETE SET NULL,

    -- SQLite counts a true condition as 1, so this reads "exactly one
    -- owner is set". An orphan attachment and a doubly-owned one are both
    -- now unrepresentable rather than merely unlikely.
    CHECK ((issue_id IS NOT NULL) + (comment_id IS NOT NULL) = 1),
    CHECK (created_by IS NULL OR created_by_external IS NULL)
);

Files rather than BLOBs, for three reasons in order of how much they bite: heap (SQLDelight maps BLOB to ByteArray, so every read of a 10 MB screenshot is a 10 MB array through a free-trial-sized JVM, where a file streams and never lands in heap); your local loop (you asked for scripts that inspect the database — one carrying every screenshot ever pasted is slow to copy and unpleasant to dump); and because it is the same volume anyway, so the BLOB's "one thing to back up" advantage is mostly notional.

The cost, honestly: writes stop being atomic. A file written whose row fails to insert leaks disk; a row deleted whose file fails to unlink does the same. Neither loses data. Handled the way the session sweep already is — a startup pass deleting files under $VOLUME/attachments/ with no matching storage_key, logged. That sweep earns its keep twice: it also collects the files behind cancelled drafts (§11).

One path resolution, not two

$RAILWAY_VOLUME_MOUNT_PATH/attachments/<storage_key>, derived from the same DatabaseLocation the database uses rather than from a second setting. One resolution means attachments cannot land on a different disk from the rows describing them — which is exactly the failure Database.kt's preamble is about: it works perfectly until the container is replaced.

11 The WYSIWYG editor

No schema impact — description and body are markdown TEXT either way.

ButtonMarkdown
Bold**text**
Italic*text*
Strikethrough~~text~~
Headings# … ######
Link[text](url)
Inline image![filename](/api/attachments/<id>)
Underline<u>text</u> — see below, D5

Underline is the one button that changes what the stored format is

No flavour of markdown has underline, deliberately — underlined text on the web means "link". Accepted resolution is inline <u>, which every renderer passes through. The consequence is that the stored document is markdown plus a little HTML, so the renderer must allow-list tags rather than pass raw HTML through. A markdown renderer with HTML passthrough, on a field any signed-in user can write and every other user will read, is stored XSS — and this is the decision that puts HTML in that field in the first place.

Inline image flow, given that "New issue" creates the row immediately: toolbar → file picker → POST /api/issues/<id>/attachments → returns an id → editor inserts ![name](/api/attachments/<id>). The issue already exists, so the attachment always has an owner and the CHECK in §10 always holds. Cancel deletes the issue; the cascade takes the rows and the sweep takes the files. Upload is gated by canEditIssue like every other write (§2) — an upload endpoint that only checks "are you signed in" is an open file host.

12 The purge — 1.sqm

Version 1 → 2. Not a real migration, and deliberately so.

Why the version must still be bumped, even though we are wiping

"We can wipe the database, so just redefine version 1" does not work, and fails silently in production only. The deployed volume already has user_version = 1 written into its header. createOrMigrateSchema() reads that, compares it to the new schema's version, finds 1 == 1, logs "schema is current" and creates nothing. The container then starts happily and every query against projects fails at runtime, against a database that believes it is up to date. No local test reproduces it, because your local volume gets wiped and takes the create path.

Bumping to 2 with a destructive 1.sqm makes the wipe automatic and idempotent: the deployed volume purges itself, and there is no Railway button to remember.

-- src/main/sqldelight/se/soderbjorn/lunicle/db/1.sqm
-- Schema 1 → 2. A PURGE, not a migration: everything from the counter-era
-- schema goes, and the MVP's tables are created from nothing.
--
-- Authorised while the design is still moving. It is also the LAST time
-- that is true: once things settle, 2.sqm and everything after it has to
-- preserve data, because by then the volume holds issues somebody wrote.
--
-- Order matters: children before parents, or the FKs refuse the drop.
DROP TABLE IF EXISTS counters;
DROP TABLE IF EXISTS sessions;
DROP TABLE IF EXISTS users;

-- …then every CREATE TABLE from §4–§10, in dependency order:
--   users, roles, projects, project_roles,
--   labels, components, statuses,
--   issues, issue_labels, issue_components,
--   comments, attachments
-- …plus the roles seed (§5), which is part of "creation" per §13.

Sessions are dropped too, which signs everyone out

Worth saying out loud, since Stage 2's whole exit criterion was that a redeploy no longer signs you out: this deploy will. sessions has a foreign key to users, and users is being recreated, so the rows cannot survive. Every browser's cookie will name a session that no longer exists, which lookup() already handles correctly — it returns null and the user sees the sign-in buttons. Nothing breaks; people just sign in again. And the first person to do so becomes the admin, which is worth knowing before you tell anyone the deploy is up.

The workflow, as server/build.gradle.kts documents it

  1. Rewrite the .sq files.
  2. Add 1.sqm above.
  3. ./gradlew :server:generateMainLunicleDatabaseSchema → writes databases/2.db, committed beside the existing 1.db.

Skip step 3 and verifyMigrations fails the build, which is the feature. Both paths are then testable locally: wipe the volume for create, or bring the container up on the current build first and then rebuild for migrate 1 → 2. The second one is the deploy, rehearsed.

13 Seeding

Two moments, not one. Accepted per D2.

  • At database creation — the three roles. Global, no project to belong to, hardcoded. Runs in createOrMigrateSchema()'s create branch and in 1.sqm, so a fresh volume and a purged one both end up with them.
  • At project creation — that project's labels, components and statuses, in one transaction with the INSERT into projects, owned by ProjectRepository (§1). A project that half-exists — a row with no board columns — would be a project you cannot file an issue in and cannot fix from the UI.

The clarification says "defaults get added on first creation of database", but labels, components and statuses all carry a project_id — at database creation there is no project to hang them on, and the first project anyone made would come up with no board columns at all. The split above is the only reading that works.

14 Decisions

Rev 2's six open questions, accepted per CLARIFICATIONS #2. Recorded so the reasoning survives the next person to wonder why.

D1 — casing: NOCASE + a Unicode check

COLLATE NOCASE for the constraint, plus a lowercase() comparison in ProjectRepository for åäö. Structural for ASCII, checked for the rest. §6.

D2 — seeding: roles at DB creation, vocabularies at project creation

A literal departure from the clarification's wording, because the literal reading cannot work. §13.

D3 — the issue's short description is title

The UI may still call it whatever you like. issue.label beside issue.labels is a bug generator. §8.

D4 — attachments: files on the volume, metadata in rows, orphan sweep

Heap and your local loop beat atomicity here. BLOBs stay a defensible fallback if the sweep ever proves annoying. §10.

D5 — underline: inline <u>, allow-listed renderer

The stored format becomes markdown-plus-a-little-HTML, so the renderer must never pass raw HTML through. §11.

D6 — labels and components are optional

"One or more" read as zero-or-more. The editor offers them; nothing rejects an issue without them. SQL cannot express a join-table minimum anyway, so the strict reading would be a server check on every write — and a rule that feels tidy on Monday gets sworn at on Friday.

D7 — projects are admin-only to mutate

Carried from rev 1 and never contradicted: any signed-in user may create a project; only an admin renames, changes settings, or deletes one. The three seeded roles are all issue-scoped, so they have nothing to say about projects — which leaves admin as the only answer the schema can give. Flagging it here because it is the one decision that was never explicitly confirmed, and it is one line in AccessControl to change. §2.
