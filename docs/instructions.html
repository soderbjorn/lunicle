Lunamux / Lunicle

Stage 1 — deploy instructions

The steps that need your accounts: Railway, the domain, and the two repos. Everything that could be built and proven without them already has been — see What's already verified before you start, so you know what you are and aren't debugging.

Step 0 The spend limit, before anything is public

Do this before the first deploy, not after

Railway → Workspace → Usage → Usage Limits. Set the hard limit. The soft limit only emails you; the hard limit is the one that actually takes workloads offline, which is the behaviour you asked for. Minimum is $10, set per-workspace. It takes two minutes and it belongs in front of the first public URL.

Nothing below this line should happen until it's set.

Step 1 Local, before Railway

Neither mode deploys anything. Both work with nothing on the internet.

Two scripts, two modes. Both run the actual Docker image Railway will build, with the same entrypoint and the same injected PORT — so they exercise the packaging, not just the code. Both wait until the server really answers, then open the right URL. Add --no-open to skip the browser, --no-build to skip the image rebuild.

Standalone — the tracker on its own

./scripts/run-standalone.sh     # → http://localhost:8080/

Just the app: no website around it, and therefore no Issues tab — that is this mode working, not failing. Framing stays restricted to lunamux.dev exactly as in production, so this mode can never prove something the deployed site wouldn't allow.

Embedded — the tracker inside the lunamux site

./scripts/run-embedded.sh       # → http://localhost:8000/?issues=1#/issues

This is the one that shows what Stage 1 is for. It serves your lunamux-web checkout with Python's built-in HTTP server (already on your Mac — nothing to install), points the tab's iframe at the container, and opens the tab. Ctrl-C stops the site; the container keeps running.

Two things make it work, and both are worth knowing because they are the same mechanisms production uses:

  • The container is started permitting http://localhost:8000 to frame it (plus lunamux.dev — frame-ancestors takes a space-separated list). Same header, same browser enforcement; only the value differs. This is the single deliberate difference from the deployed configuration; run-standalone.sh uses production's policy untouched.
  • lunamux-web frames localhost:8080 instead of lunicle.lunamux.dev when the site itself is served from localhost (SITE.issues.devIframeSrc). That choice keys off your own hostname and never off a query parameter — a visitor-supplied iframe URL on the live site would let any link frame arbitrary content inside lunamux.dev.

Override the paths and ports with LUNAMUX_WEB, LUNICLE_PORT, SITE_PORT if the defaults don't fit.

The easy mistake: two URLs, one of them tab-less

:8080 is the tracker standalone — a bare counter, no site, no tab. :8000/?issues=1#/issues is the site with the tracker inside its Issues tab. Landing on :8080 when you wanted the embed looks exactly like "the embed is broken" while nothing is wrong at all. That is why container-up.sh opens no browser of its own and the run scripts each open only their own URL.

The container underneath

./scripts/container-up.sh       # build + run the image, nothing else
./scripts/container-down.sh     # stop and remove it

Lifecycle only — no site, no browser. The run scripts call container-up.sh for you, so you rarely need it directly; container-down.sh is how you stop the container either script leaves running. container-up.sh starts Docker Desktop if it isn't running, replaces any previous instance so re-running after a code change just works, and dumps the container's logs if it fails to come up. Switching between the two modes re-creates the container with that mode's framing policy, so a stale policy can't linger.

Also there: dev-local.sh

./scripts/dev-local.sh (and --embed) does the same two modes straight from Gradle, with no Docker. It is much faster to iterate against — an incremental Kotlin build in seconds, rather than a full rebuild inside the image — so it's the one to reach for while changing code. The two scripts above are what you want when the question is "does the thing I'm about to deploy work".

What this does and doesn't buy you

It proves the framing contract, the lazy-load, the nav gate and the round-trip — cheaply, and without a deploy. It does not prove DNS or the certificate, because localhost has neither. Those are exactly what Steps 3–4 exist to establish, and they are the parts that can still bite.

Step 2 Railway

  1. This repo already points at github.com:soderbjorn/lunicle (private).
  2. Railway → New Project → Deploy from GitHub repo → pick it.
  3. Railway detects the Dockerfile at the repo root and uses it. No buildpack, no Nixpacks, no configuration — that is the whole point of shipping a Dockerfile.
  4. Leave PORT alone. Railway injects it and the server reads it at runtime (resolvePort() in Application.kt). Hard-coding a port here is the classic way to get a service that builds, boots, and never answers.
  5. Set no other variables. FRAME_ANCESTORS defaults to https://lunamux.dev, which is what production wants; it exists as an override for local runs and preview deploys.

The build is slower than you'll expect the first time

The image compiles Kotlin/JVM and Kotlin/JS, and the JS half downloads a Node toolchain and an npm tree inside the build. Several minutes cold is normal, not a hang. The Dockerfile copies the build files before the sources specifically so this layer caches and a source-only edit doesn't pay it again.

Step 3 The domain — Railway side

  1. Railway → your service → Settings → Networking → Custom Domain.
  2. Enter lunicle.lunamux.dev.
  3. Railway shows a CNAME target (something like <id>.up.railway.app). Copy it — Step 4 needs it. It is specific to your service; don't guess it.

Step 4 The domain — Cloudflare side

  1. Cloudflare → lunamux.dev → DNS → Records → Add record.
  2. Type CNAME, name lunicle, target = the value from Step 3.
  3. Proxy status: DNS only (grey cloud). Not orange. See below.

Grey cloud first — this is the one that wastes an afternoon

Railway issues the certificate for lunicle.lunamux.dev itself, via Let's Encrypt, and to do that it must be reachable at that name. With Cloudflare's proxy on (orange cloud), Cloudflare terminates TLS and answers the validation challenge, so Railway's issuance can fail or hang — and you get a certificate error on a service that is otherwise working perfectly.

So: grey cloud, let Railway issue the certificate, confirm the site loads over HTTPS. Only then consider turning the proxy on — and if you do, Cloudflare SSL/TLS mode must be Full (strict). Anything less (Flexible especially) gives you either a redirect loop or Cloudflare talking plaintext to Railway, which is worse than it sounds.

Honestly: Stage 1 has no reason to want the proxy. Grey cloud is the answer here.

DNS propagation is usually a minute or two, not the mythical 48 hours. Check it directly rather than refreshing a browser tab and guessing:

$ dig +short lunicle.lunamux.dev
$ curl -sI https://lunicle.lunamux.dev/ | head -1
$ curl -sI https://lunicle.lunamux.dev/ | grep -i content-security

That last one should print frame-ancestors 'self' https://lunamux.dev. If it doesn't, the embed in Step 5 will be a blank rectangle and you'll be debugging the wrong layer.

Step 5 Publish the secret tab

The lunamux-web edits are already made in your local checkout but not committed. Review them, then commit and push — GitHub Pages serves that repo, so pushing is publishing.

Five files, mirroring the demo page's pattern rather than inventing one:

FileEdit
content.jsnavHidden (the gated tab, as data) and the issues page block with its prod + local iframe URLs.
index.htmlThe #page-issues container.
render.jsThe nav gate (URLSearchParams) and the iframe markup with its data-src.
script.jsPage registration, ensureIssuesLoaded(), and the chromeless body class.
styles.cssThe demo's chromeless iframe rules, extended to cover the issues embed.

Then the URL is:

https://lunamux.dev/?issues=1#/issues

The parameter is in the query string, before the hash, so the hash router never sees it.

"Secret" means undiscoverable, not protected

lunamux-web is a static site. The tab, the parameter name and the lunicle.lunamux.dev URL are all sitting in content.js for anyone who opens view-source, and the server is publicly reachable regardless of what the marketing site links to. Fine for what you want — no links, nobody stumbles in — as long as it is never mistaken for an access control. Note that #/issues stays routable without the parameter: the gate hides the tab, and that is all it was ever asked to do. When Stage 2 adds real users, the server enforces that itself.

Step 6 Exit criteria

Straight from stages.html. The first two are the ones that matter.

Check, in order

  • Load https://lunamux.dev/?issues=1#/issues in Chrome and Safari. The counter increments inside the iframe.
  • Redeploy the container. The count resets to zero — that's correct, it proves the count was the server's and the server is genuinely new.
  • The Railway hard limit is set. (Step 0. If you skipped it, do it now.)
  • No console errors.

If the iframe is a blank rectangle

Open the console. "Refused to frame … violates the following Content Security Policy directive" means the header is wrong or missing — check Step 4's curl, and check that Cloudflare's proxy isn't stripping or replacing it. That message is the good failure: it tells you exactly which layer to fix. A blank frame with a certificate error instead means Step 4's grey-cloud advice was skipped.

Notes Where things stand

  • Both repos are committed and pushed. This one to soderbjorn/lunicle (private), and the tab edits to soderbjorn/lunamux-web. Note what the second one means: GitHub Pages serves that repo, so the Issues tab is live on lunamux.dev now — and because lunicle.lunamux.dev doesn't exist until Steps 2–4 are done, opening ?issues=1#/issues today gives an empty frame. Nobody without the parameter sees anything change.
  • The image is 509 MB. Fine for now, and not worth optimising before it has ever run in anger. A jre-alpine base or a jlink'd runtime is the lever if cold-start time ever annoys you.
  • The bundle is the production one (~700 KB), unlike Lunamux itself, which deliberately ships its dev bundle to dodge a Kotlin/JS optimizer miscompilation. That bug is layout-sensitive, so this being a much smaller codebase is a reason to expect it to be fine — not a proof. It renders correctly in Chrome today. If a console error like "<mangled> is not a function" ever appears, that is what it is, and server/build.gradle.kts has the two lines to swap and a comment pointing at Lunamux's write-up.
  • Stage 2 will need two more headers — allow="identity-credentials-get" on the iframe element and Cross-Origin-Opener-Policy: same-origin-allow-popups on the server — because Google's consent screen cannot be framed. Not needed yet; noted so the iframe markup's shape isn't a surprise later. See stages.html §Stage 2.
