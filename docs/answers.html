01How email actually moves — who hosts what

"explain the email transmission mechanism. would it be cloudflare hosting it? would it host smtp servers? more detail please."

Short answer

You never run an SMTP server, and your Ktor code never speaks SMTP. Two different vendors handle two independent directions: Cloudflare hosts the receiving SMTP servers, Resend hosts the sending ones. Your server just makes an HTTPS POST. The two halves don't know about each other.

The confusion is worth clearing up properly, because "email" is really three separate flows that happen to share a domain name. Let's take them one at a time.

Flow A — Someone emails hello@lunamux.dev

Yes, Cloudflare hosts real SMTP servers here. Those route1/2/3.mx.cloudflare.net MX records point at actual mail transfer agents listening on port 25, operated by Cloudflare. That's what an MX record is — a pointer to a machine that accepts SMTP connections for your domain.

Inbound — your server is not involved at all

  someone@example.com
          │
          │ 1. their mail server asks DNS: "MX for lunamux.dev?"
          │    → route1.mx.cloudflare.net, route2…, route3…
          ▼
  ┌────────────────────────┐
  │  Cloudflare MX servers │  ← real SMTP servers, port 25,
  │  (Email Routing)       │    run by Cloudflare, free
  └────────────────────────┘
          │ 2. rejects the mail outright unless it passes SPF or DKIM
          │ 3. matches your rules: catch-all *@lunamux.dev → robert@soderbjorn.se
          │ 4. SRS-rewrites the envelope sender so SPF still validates,
          │    adds DKIM signatures + an ARC seal. From: header untouched.
          ▼
  ┌────────────────────────┐
  │  Google Workspace      │  ← ASPMX.L.GOOGLE.COM, your existing MX
  │  (soderbjorn.se)       │
  └────────────────────────┘
          │
          ▼
     your Gmail inbox          ← lands here. Zero code. Pure DNS + config.

Nothing you write runs in this path. You don't have a mailbox on lunamux.dev in any real sense — Cloudflare accepts the mail on that domain's behalf and immediately hands it to Google, who store it. That's why it's free and why there's no storage limit to think about: Cloudflare is a relay, not a mailbox provider.

Flow B — Your server sends a verification email

This is the one people picture as "sending mail from the server", and it isn't. Your Ktor code makes an ordinary HTTPS request. No mail library, no JavaMail, no port 25, no queue, no retry logic.

Outbound transactional — your server speaks HTTPS, not SMTP

  ┌────────────────────────┐
  │  Your Ktor server      │  POST https://api.resend.com/emails
  │  (Railway)             │  { from, to, subject, html }
  └────────────────────────┘  ← plain HTTPS + JSON. ~10 lines of Ktor client.
          │
          │ HTTPS, port 443
          ▼
  ┌────────────────────────┐
  │  Resend                │  queues it, signs DKIM with d=send.lunamux.dev
  │  (runs on Amazon SES)  │  using the key you published in DNS
  └────────────────────────┘
          │ SMTP, port 25 — Resend's MTAs do this part, from their IPs
          ▼
  ┌────────────────────────┐
  │  Recipient's MX        │  checks SPF  → include:amazonses.com  ✓
  │  (gmail.com, etc.)     │  checks DKIM → your published key       ✓
  └────────────────────────┘  → DMARC aligns → inbox

Incidentally, that feedback-smtp.eu-west-1.amazonses.com MX record Resend asks you to add is the tell that Resend is built on Amazon SES. It's their bounce-handling address. That's fine — it's what you're paying them (nothing) to abstract.

Flow C — You reply from Gmail as hello@lunamux.dev

Here's the bit that answers "how can Gmail impersonate a domain it doesn't host". It doesn't deliver the mail — it hands it to Resend. Gmail acts as an SMTP client, authenticating to someone else's SMTP server:

Send-as — Gmail as an SMTP client, not a sender

  You hit Send in Gmail
          │
          │ Gmail connects OUT to smtp.resend.com:587
          │ username "resend", password = your API key, STARTTLS
          │ ↑ this is exactly what the Workspace admin toggle
          │   "allow per-user outbound gateways" permits
          ▼
  ┌────────────────────────┐
  │  Resend                │  signs with your DKIM, delivers as in Flow B
  └────────────────────────┘
          │ SMTP, port 25
          ▼
     recipient                 ← sees a properly aligned lunamux.dev email,
                                  no "via gmail.com", DMARC passes

An "outbound gateway" is just the mail world's term for relay through a third party's SMTP server. Google's default is to send through their own servers, which is why the DKIM would say d=gmail.com and DMARC would fail. Pointing it at Resend is what makes the identity honest.

Why you must not run your own SMTP server

Worth spelling out, since it's the obvious next question and the answer is unusually one-sided. Self-hosting mail is one of the few places where "just run it yourself" is genuinely bad advice:

  • Port 25 is blocked outbound. Railway, AWS, GCP, Azure, DigitalOcean — all block it by default, precisely because spammers. This alone ends the conversation before reputation even comes up.
  • A fresh IP has no sending reputation. Gmail and Outlook will spam-folder or reject you outright, and there's no appeal — you earn reputation over months of consistent, wanted volume you don't have.
  • You need reverse DNS (PTR) matching your HELO. On Railway you don't own the IP, so you cannot set it. Many receivers reject on that alone.
  • Shared IPs. On a PaaS your outbound IP is shared. Someone else's spam becomes your deliverability problem.
  • And then the actual work: bounce handling, suppression lists, feedback loops with each ISP, DKIM key rotation, TLS for the MTA, queue management, retry backoff. Resend and SES exist because this is a specialty, not a weekend.

Receiving is no better: you'd need port 25 open inbound, an always-on process, spam filtering, and somewhere to store the mail. Cloudflare does all of it for free and better.

The one-vendor alternative, if you'd rather

Cloudflare can now do both halves. Email Service added outbound sending (public beta April 2026) and authenticated SMTP submission (June 2026): smtp.mx.cloudflare.net:465, implicit TLS only — note 587/STARTTLS is not supported, which matters because Gmail's send-as UI wants 587 or 465, so you'd pick 465/SSL there.

It needs the Workers Paid plan at $5/mo, then 3 000 emails included and $0.35 per 1 000 after. So: one vendor, one dashboard, one set of DNS records — for $5/mo and an overage meter, versus Resend's $0 and a hard 429. I'd still take Resend, because "cannot be billed" is worth more to you than "one fewer dashboard", but it's a legitimate call and worth knowing the option exists. Third-party blogs cite $0.09/1 000 for this; the official pricing page says $0.35. Trust the official number.

What you actually build

The entire email surface in your codebase is roughly this — one function, no dependencies beyond what Ktor already gives you:

suspend fun sendVerificationMail(to: String, token: String) {
    client.post("https://api.resend.com/emails") {
        header(HttpHeaders.Authorization, "Bearer $resendApiKey")
        contentType(ContentType.Application.Json)
        setBody(SendMailRequest(
            from    = "Lunamux Issues <noreply@send.lunamux.dev>",
            to      = listOf(to),
            subject = "Verify your email",
            html    = verifyTemplate("$baseUrl/verify?t=$token"),
        ))
    }
}

That's it. Everything else in §7 of the analysis — SPF, DKIM, DMARC, the subdomain split — is DNS configuration you do once in a browser, not code.

02Single-operator instances: what this simplifies

"clarification on creating projects: my own hosted server would only host my own projects. but since the whole thing should be open source, others might want to set up their own hosted version of the issue tracker for their projects."

Good news

This is a meaningfully simpler product than what I'd hedged against, and it deletes a category of work. You're building multi-project, single-operator software, not a multi-tenant SaaS. The distinction is the difference between shipping software and operating a platform.

I'd written §2 defensively because "multiple projects, embeddable in each project's site" reads like the start of a hosted service. Your clarification settles it: each deployment has exactly one operator, who owns every project on it. Yours has your projects. Someone else deploys their own container for theirs. Nobody's projects share a server with a stranger's.

What this deletes

  • Cross-tenant abuse liability. I warned about someone else's project spamming from your sending domain and torching your reputation. Can't happen — nobody else has a project on your instance.
  • Content moderation. You're not responsible for policing what strangers file under a project you've never heard of.
  • Per-tenant support burden. Someone else's outage is their container, not your Saturday.
  • Per-project sending domains. This one's a real saving — see below.
  • Tenant isolation as a security boundary. Project scoping is still a correctness concern (don't leak project A's issues into project B's view), but it's no longer a security boundary between mutually distrusting parties. Much lower stakes if you get a query wrong.

What survives — and it's the important one

Accounts are still public. Projects are not.

Anyone on the internet can create an account on your instance to file an issue against Lunamux — that's the whole point. So every word of §7's abuse section still applies at full strength: rate limit per target email address, Turnstile on the form, a hard daily send cap in code. The public surface didn't shrink; only the project creation surface did.

The two are easy to conflate. "Only my projects" makes it sound like a private tool. It isn't — it's a public signup form attached to a private project list.

Sending domain: now settled

In the analysis I hedged: "either keep one sending identity for everyone, or let each project verify its own domain", and recommended the former on complexity grounds. Your clarification makes it not a choice at all. One operator = one sending identity per deployment, full stop:

MAIL_FROM=Lunamux Issues <noreply@send.lunamux.dev>
RESEND_API_KEY_FILE=/run/secrets/resend

Two env vars. A self-hoster sets noreply@send.theirdomain.com and their own key. There is never a per-project DKIM key, never a per-project reputation, never a "why is project X's mail bouncing" ticket. That's a whole subsystem that doesn't need to exist.

How projects should get created

This falls straight out of the model, and I think it's genuinely the nicest part of the clarification. You don't need an admin UI at all for v1. Projects are operator-controlled configuration, so declare them in a config file, mounted into the container, upserted into the DB by slug at startup:

# /config/projects.yaml — mounted, version-controlled, no UI needed
projects:
  - slug: lunamux
    name: Lunamux
    allowed_origins:
      - https://lunamux.dev
    theme:
      bg:        "#04090f"
      panel:     "#070f1a"
      accent:    "#4dc8f5"
      accent_hi: "#66d9ff"
      head:      "#eaf3fb"

  - slug: darknessirc
    name: Darkness IRC
    allowed_origins:
      - https://darknessirc.soderbjorn.se
    theme: { ... }

Why this shape:

  • No admin UI to build, secure, or document. The single largest chunk of work you'd otherwise do before v1.
  • Version-controlled. Project config lives in git next to everything else; changes are reviewable and revertible.
  • Self-hosters get a file they can read. Far better than "click through six screens" as install documentation, and it's what makes your README short.
  • Theme and origin allowlist live together, which is exactly where §9 and §3 want them.
  • Slug is stable identity, so upsert-by-slug is idempotent — restart the container as often as you like.

This is a small, deliberate exception to the "env vars, not config files" rule in §10. Env vars are right for scalars — a database path, an API key. A nested list of projects with per-project themes and origin lists is not a scalar, and cramming it into PROJECTS=lunamux:Lunamux:#04090f,… is the kind of thing that's clever for a week and miserable forever. Keep env vars for everything else.

Also: multi-project is now clearly worth it

Worth saying plainly, since "do I even need this" is the reasonable question. Yes. Without it you'd run one container, one volume, one domain, one Railway service per project — and pay Railway's $5 floor for each. With it, every project you ever start is a five-line entry in a YAML file on infrastructure you're already paying for. That's the feature paying for itself at project number two.

The embedding story gets easier too

I checked what's actually deployed: only lunamux-web (→ lunamux.dev) and termtastic-web (→ termtastic.soderbjorn.se) have sites today. That means future projects will land either on their own domain or on a soderbjorn.se subdomain — and you control the DNS for all of them.

So the per-project CNAME recommendation from §3, which I framed as needing coordination with project owners, is really just you adding a DNS record to a zone you already administer. No emails to third parties, no waiting. Each project's site gets:

issues.lunamux.dev              CNAME → your-app.up.railway.app
issues.darknessirc…             CNAME → your-app.up.railway.app

…and every embed is same-site with its parent, so the entire cross-site cookie problem never arises in any browser. Same for self-hosters: they own their domains too. The design that was defensive is now just the obvious one.

Worth noting the alternative you now have: if most projects end up on soderbjorn.se subdomains, hosting the tracker at issues.soderbjorn.se would make those same-site for free, with only lunamux.dev needing its own CNAME. But the uniform per-project CNAME works everywhere and costs one record either way, so I wouldn't optimise for it.

03Scaling and multiple instances

"would i need multiple instances of the server for scaling? what would be the implications - in general, and for database access?"

Blunt answer

No — and with SQLite you can't, which is worth being explicit about. SQLite hard-caps you at exactly one instance, and Railway enforces the same limit independently: "Replicas cannot be used with volumes." So this isn't a knob you'll be tempted to turn and get wrong. The real question is whether you'd ever want to, and what the exit looks like.

Would you ever need to? Almost certainly not

The numbers aren't close:

  • Railway Hobby lets one service scale to 48 GB RAM and 48 vCPU. That's a large machine, and it's a slider, not an architecture change.
  • A Ktor/Netty JVM app on 1 vCPU and 512 MB handles hundreds of requests per second for a workload like this.
  • An issue tracker for tens of users is a handful of requests per second at peak, overwhelmingly reads.
  • SQLite's own guidance puts the threshold around 100k hits/day; sqlite.org itself serves 400–500k requests/day on it, and Expensify runs it at millions of users.

You'd hit thousands of concurrent users before a single instance became the constraint — and long before that you'd notice, because CPU and p99 latency would tell you. Vertical scaling is the answer, and it's a slider you probably never touch.

What one instance actually costs you

Two things, and both are already true regardless of replicas:

  • No high availability. If the container dies you're down until it restarts. Worse, Railway's healthchecks run at deploy time only — there's no ongoing liveness probe, so a JVM that deadlocks at 3am stays deadlocked until you notice. Worth an uptime check (Cloudflare, UptimeRobot, whatever) pointed at /health.
  • Deploys have downtime. A few seconds while the old container releases the volume and the new one mounts it. You lose this to the volume constraint whether or not you ever wanted replicas — Railway won't let two deployments mount one volume, so healthchecks can't do a zero-downtime handover.

For an issue tracker, both are fine. For something with an SLA, neither would be. Know which one you're building.

What would break if you went multi-instance

This is the interesting part of your question, because the answer is "more than just the database" — and one of them is a security regression rather than a performance one:

ConcernOne instanceN instances
Database SQLite file on the volume Broken. SQLite is a library, not a server — the DB is a local file. Two instances means two different files, or one file over a network FS, which is silent corruption (§6). You must move to Postgres. Not optional.
Rate limiting In-memory counters Counters are per-instance, so N instances = N× the effective limit. Your "3 verification emails per address per day" quietly becomes 3N. This is a security regression, not a perf one. Needs DB- or Redis-backed counters.
Litestream One process, one WAL Must run exactly once per database. Two replicating the same DB corrupts the replica. Moot anyway — you'd have dropped SQLite.
Scheduled jobs Run once Run N times. Needs a DB lock or leader election.
In-memory caches Consistent Diverge per instance → inconsistent reads.
WebSockets (if you add live updates) Trivial Connections pin to one instance; broadcasting needs a pub/sub bus.
Sessions Fine Already fine — see below.

One thing you already got right

The stateless AES-GCM session token pattern I recommended borrowing from FramnaFolk (§3) means no session table and no sticky sessions. Any instance can validate any request, because the session is self-contained in the encrypted cookie. That's the piece that usually forces sticky load balancing or a Redis session store, and you'd get it for free. Nice accident of following your own precedent.

Database access specifically — why SQLite is the hard stop

Worth understanding the mechanism rather than the rule, because it explains why there's no clever workaround. Postgres is a server: your app opens a TCP connection and the server arbitrates concurrent access across every client. SQLite is a library compiled into your process: your app opens a file, and coordination happens through filesystem locks.

Filesystem locks only work between processes on the same machine, on a real local filesystem. Two Railway replicas are two machines. There is no lock they can share. And as §6 covers, the network-filesystem workaround is the dangerous one — NFS/EFS emulate mmap coherency and advisory locking well enough to appear to work, so both instances think they hold the write lock, and you get silent corruption rather than an error. That's why Railway simply forbids the combination: they're saving you from it.

So: SQLite and horizontal scaling are mutually exclusive by construction. Not a limitation to engineer around — a property of what SQLite is.

The exit, if you ever need it

This is why the repository interface from §6 matters, and it's the concrete payoff for a recommendation that otherwise sounds like generic hygiene:

  1. Write a Postgres implementation of the repository interface. Bounded work, confined to the data layer — if you kept the SQL boring (no FTS5, timestamps as epoch-millis INTEGER, UUIDs as TEXT).
  2. Move rate limiter state into the database. Small, and you'd want it anyway.
  3. Drop Litestream — Postgres has its own backup story.
  4. Add a DB lock for scheduled jobs.
  5. Turn up replicas. Sessions already work; nothing else is stateful.

That's maybe a week, and it's a week you'd spend once you have the traffic to justify it — with real numbers, on a schema that's stopped moving. Doing it now costs the same week, plus the permanent tax of a dual-dialect test matrix (§6), to solve a problem you don't have.

Cheaper levers, in the order you'd actually reach for them

1. Vertical scale. A slider in Railway. Covers you to thousands of users.
2. Cloudflare cache in front of anonymous/public issue views. If a project's issues are publicly readable, that's your read traffic gone at the edge for free, without touching the app.
3. Then, and only then, Postgres + replicas.

Most projects that "need to scale" needed step 2.

Recommendation

One instance. Vertical scaling. Don't design for horizontal. Keep the repository interface and keep the SQL portable — that's an afternoon of discipline now and it's the entire migration path later. Revisit when you have evidence: CPU saturation, p99 latency, an actual complaint. Not before.

And for an open-source self-hosted tracker, "runs as exactly one instance" is a completely unremarkable constraint. Vaultwarden, Gitea-on-SQLite, Miniflux — same shape. Nobody will file an issue about it.
