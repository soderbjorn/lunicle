Lunamux / Lunicle

The scripts, and which one you want

Everything here runs on your machine. Nothing in this directory deploys, and nothing touches Railway, Cloudflare, or the live site. Every script explains itself at the top of its own file — this page is the map between them.

Start Four ways to run it

Two questions, two answers each. The names are the answers.

Every run script is run-<what>-<how>.sh. What runs the tracker, and how it is presented. Those two choices are independent, which is why there are four:

standalone — the app alone embedded — inside the lunamux site
dev — your working tree run-dev-standalone.sh
→ localhost:8080/		 run-dev-embedded.sh
→ localhost:8000/?issues=1#/issues
container — the Docker image run-container-standalone.sh
→ localhost:8080/		 run-container-embedded.sh
→ localhost:8000/?issues=1#/issues

Choosing the row: dev or container?

  • dev runs the code you just edited, via Gradle. An incremental Kotlin build takes seconds. This is the one to reach for while writing code.
  • container runs the image you last built — the same image Railway builds, with the same entrypoint, the same injected PORT, and a real Docker volume. It exercises the packaging and the deploy mechanisms, not just the code. Reach for it when the question is "does the thing I'm about to deploy work?"

The container runs what you BUILT, not what you edited

A run-container-*.sh without --no-build rebuilds the image first, so it picks your changes up. With --no-build it does not — which is fast and correct when you meant it, and a genuinely confusing five minutes when you didn't.

Choosing the column: standalone or embedded?

  • standalone is the app on its own on :8080. There is no website around it and therefore no Issues tab — that is this mode working, not failing. Framing stays restricted to lunamux.dev exactly as in production, so this mode can never prove something the deployed site wouldn't allow.
  • embedded serves your lunamux-web checkout on :8000 with Python's built-in HTTP server and points the Issues tab's iframe at your tracker. This is the one that shows what Stage 1 is for.

The easy mistake: two URLs, one of them tab-less

:8080 is the tracker standalone — no site, no tab. :8000/?issues=1#/issues is the site with the tracker inside its Issues tab. Landing on :8080 when you wanted the embed looks exactly like "the embed is broken" while nothing is wrong at all. That is why each run script opens only its own URL, and container-up.sh opens none.

Flags: all four take --no-open. The two container ones also take --no-build. Anything else is a usage error rather than a silently ignored typo.

Also The supporting cast

You need these less often, and never to just run the thing.

ScriptWhat it's for
stop.sh Stops whatever you have running, whichever way you started it, and never deletes data. --status says what's running and changes nothing. Reach for this when a run script says the port is taken.
local-db.sh The dev database at ~/.lunicle/: path, inspect, dump, sql, seed, admin, wipe. Only the dev row of the matrix uses it — the container has its own volume.
container-up.sh
container-down.sh		 Container lifecycle, nothing else: no site, no browser. The run-container-* scripts call up for you, so you rarely need it directly. down is how you stop the container they leave running; down --wipe also deletes the database volume.
container-entrypoint.sh Not a script you run. It is copied into the image and is its entrypoint — see the Dockerfile. It starts as root, chowns the mounted volume, and drops privileges. Renaming it means editing the Dockerfile and .dockerignore too.
lib/*.sh Sourced, never run. See below.

Deliberate: down keeps the data

container-down.sh keeps the volume, so down, up, and your data is still there is the local rehearsal of the production exit criterion. --wipe is for the other half — proving the fresh-volume path still works, which is a code path production runs exactly once, on the first deploy, where getting it wrong is most expensive and least observable.

lib/ The shared parts

Sourced by the scripts above. Each fact lives in exactly one of these.

These exist because the four run scripts genuinely share most of their work, and the shared parts carry hard-won reasoning that must not be allowed to drift into four slightly different copies. If you are about to copy a block between scripts, it probably belongs here instead.

FileOwns
lib/env.sh Loading .env, and the list of OAuth providers (LUNICLE_OAUTH_VARS) — shared because the Gradle path turns each into a -P property and the container path into a -e variable, and adding a provider while updating only one of those is the drift this prevents.
lib/probe.sh "Is it up?" and "who holds the port?" — including why the readiness probe hits /api/session and not /api/counter, and why lsof needs -sTCP:LISTEN.
lib/dev-server.sh Starting, waiting for, and reaping the Gradle-run server — plus the marker that identifies it, and the whole -P-not-environment story.
lib/site.sh Serving the lunamux-web checkout: the python server, the framing check, the Issues-tab banner. Both embed scripts differ only in what serves the tracker; the site half is identical and lives here once.
lib/browser.sh Opening the browser, and honouring --no-open.

Why -P properties instead of environment variables

The one piece of background that explains most of lib/dev-server.sh: :server:run is a Gradle JavaExec, so the server inherits the long-lived daemon's environment, not your shell's. An exported variable is therefore whatever the daemon started with and stays that way, invisibly, until the daemon dies — which has bitten the port, the framing origin, and every OAuth secret in turn. A -P property is per-invocation and cannot drift. The deployed container does use environment variables for all of these: there is no daemon there, and it is how Railway supplies them.

Env Knobs

All optional. The defaults are what you want.

VariableDefaultEffect
LUNICLE_PORT 8080 The tracker's port. Useful when something else holds 8080 and you'd rather not fight it.
SITE_PORT 8000 The local lunamux-web port. Embed scripts only.
LUNAMUX_WEB ../../lunamux-web Where your lunamux-web checkout is. Embed scripts only.
LUNICLE_LOCAL_DATA ~/.lunicle Where the dev row keeps its database and attachments. Read by local-db.sh and the run-dev-* pair alike, so they can't disagree about which database is the real one.
FRAME_ANCESTORS set per mode Overrides the framing policy for the container. Each run script sets it to what its mode means, so you should not normally touch it.

OAuth credentials live in a gitignored .env at the repo root — see .env.example and oauth-instructions.html. Absent is fine and silent: the server just offers no sign-in.
